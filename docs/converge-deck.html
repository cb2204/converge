01 · INTRODUCTION

What is Converge? The factory where done is proven.

Converge compiles intent into software. Whatever coding agent you run — Claude Code, Codex, Kimi, Grok Build — it works against signed task specs whose completion is enforced by evals, not by the agent's word. Every task ships with runnable bash evals authored before the work; a task only settles when those evals exit green.

The unit of work is the Task-Spec: a self-verifying markdown file with a machine-checked format, an effort budget, an HMAC sign-off seal, and its own definition of done. The cvg CLI is the referee around it — it frames, dispatches, and gates, but holds zero model credentials and never writes a line of product code.

“Agents play; the referee scores.” PLAIN BASH + STDLIB PYTHON — THE SAME INSTALL SERVES EVERY HARNESS
WHY · 01

The eval decides done

A task cannot settle until its evals exit 0 — completion is a state-machine invariant. The maximal stub attack (all nine specs faked) lands all nine RED.

WHY · 02

The referee is never a player

cvg holds no API keys and calls no models. Engine CLIs authenticate themselves; the referee only frames, dispatches headlessly, and gates.

WHY · 03

Cross-family verification

Tier-2 acceptance sends the diff, the intent, and holdout criteria the builder never saw to a different vendor's model, prompted to refute.

WHY · 04

A loop with brakes

Attempt → verify → repeat under three-axis budgets, a stagnation detector, and eight named terminal states. An exhausted budget is never a success.

01 · INTRODUCTION — THE VOCABULARY

Twelve words that carry the whole system.

THE SHAPE

The descent

The nine-gate production line, pass 0 → 8. A raw idea goes in; merged, proven work comes out. Evidence and lessons flow back to feed the next pass.

THE UNIT OF METHOD

Pass

One installable skill with one job, one output, one gate. You or your agent do the work; the gate proves it happened.

THE VERDICT

Gate & token

A deterministic script whose verdict ends in one greppable token (CHECK_PLAN=OK). Fail-closed: a verdict that cannot be read is never a pass.

THE UNIT OF WORK

Task-Spec

A self-verifying markdown file: machine-checked format, effort budget, HMAC seal, and its own definition of done. The evals travel inside the file.

THE JUDGE

Eval

Runnable bash authored before the work. The eval decides done — completion is a state-machine invariant, never an agent's claim.

THE TRUST DEVICE

The seal

An HMAC-SHA256 envelope over the spec's identity, body digest, and authorization fields. Edit one eval byte after signing and the gate refuses.

PASS 4

The barrier

A different-family model attacks the plan; the owner resolves objections and signs. The last human decision in the chain.

PASS 5

The cornerstone

Where intent becomes signed, self-verifying Task-Specs — the point of no return between the design half and the machine half.

THE ROUTER

Lane

cvg lane routes work to the ceremony it earns — FAST (5, 7, 8) · NORMAL (1, 2, 5, 7, 8) · FULL (0–8). It routes, but never waives.

THE UMPIRE

The referee

cvg — frames, dispatches, gates. Holds zero model credentials, calls no models, writes no product code. Agents play; the referee scores.

THE TERMINAL STATE

Settled

Green evals within budget, receipt written, PR opened — TASK_LOOP=SETTLED. An exhausted budget is never a success.

THE FLOOR

Evidence

Receipts, seals, tokens, objection logs, attempt transcripts — the artifacts every gate stands on. cvg next derives the whole descent's position from them.

The three layers: the Agentic Loop is the runtime (attempt → verify → repeat) · Converge is the method (nine gated passes) · ASD — Agentic Software Delivery — is the meta-process that turns every run's evidence into the next run's input.

02 · THE METHOD — GATES, TOKENS & EVIDENCE

How a gate works. Fail-closed, byte-exact, greppable.

THE MECHANICS

Every wrapped gate is a byte-exact pass-through (exec) to the proven skill script — the router adds convenience, never behavior. Each verdict ends in one token on its own line, so a script, a CI job, or an agent can read the outcome with a single grep. Artifacts are discovered in typed folders (cvg/docs/brd/, then legacy paths) — zero found is exit 2, never a silent pass.

FAIL-CLOSED, EVERYWHERE

A verdict that cannot be obtained is never a pass: a missing engine is SKIP, a wall-clock breach is TIMEOUT, an unparseable judgment is ENGINE_ERROR. Gate checks run with fenced code blocks stripped, so pasting the magic words inside a code sample authorizes nothing. Sentinels like (open), tbd, pending read as unresolved — anything the script cannot prove resolved counts against you.

THE CONDUCTOR — cvg next

Derives which pass is current and which comes next from workspace evidence alone — no stored state. It prints the evidence board, the owning skill, its steering prompt, and the pass's closing gate. Presence probes only: evidence presence is not a verdict — the gates stay authoritative. Pre/post hooks enforce descent order fail-closed. NEXT_PASS=0-8|DONE

03 · THE PASSES — CAPTURE

Capture — grill the gaps out of the idea.

SKILL · idea-to-brd GATE · CHECK_BRD=PASS OPTIONAL · FULL LANE IN · A RAW IDEA OUT · cvg/docs/brd/<slug>.md
WHAT YOU DO

The skill grills the stakeholder, not the engineer, in frontier rounds — every answerable question goes out at once, numbered, each with a recommended default. Seven branches in leverage order: pain → the do-nothing test → goal → scope boundary → success from the owner's seat → constraints → the pre-mortem (“it shipped and failed — what killed it?”).

WHAT THE GATE PROVES

The brief is complete and signed: verdict line canonical in the owner's hand, a calendar-real date, every number provenance-tagged, every open question owned. Checks run with fenced code blocks stripped — evasion by example is blocked.

THE CLI PATH
1cvg capturethe BRD exit contract
2cvg capture --draftprogress check — never authorizes
3cvg capture --no-govalidate the parked record
CHECK_BRD=FAIL

A (guessed) number with no linked open question fails. A scope entry that says nothing fails. A heading that drifts from the template fails. Owner-voice is a WARN; structure is law.

cvg/docs/brd/storm-alerts.md ANATOMY OF A BRD
## Executive summary — written LAST, ≤ 60 words
## Problem — every number tagged (measured) / (estimated) / (guessed)
## Goals & KPIs — in the owner's terms, not the engineer's
## Scope — in / out, each entry earns its line
## Definition of success · ## Stakeholders · ## Risks · ## Constraints
## Open questions — every one carries a named owner
## Sign-off  verdict: canonical  date: 2026-08-04 — born _pending_, only the owner flips it
THE DO-NOTHING EXIT
cvg/docs/no-go/<slug>.md

If the do-nothing cost is tolerable: the idea in two lines, the owner of the call, the do-nothing answer verbatim, and what would reopen it. Parked, not deleted — and no handoff from a no-go.

ANSWER DISCIPLINE
Locked: 1 — <answer>

Answers are locked by restating. Push back once per vague answer; after two carries an unanswered question becomes an owned open question, never a silent gap.

WHAT YOU DO

Read the BRD as the senior engineer accountable for delivery. The admission rule: a requirement enters the spec only if a future eval could pass or fail it. Non-falsifiable wishes go to the open-assumptions list with a named owner — never softened into the spec.

WHAT THE GATE PROVES

Verdict canonical with a valid date, and no blocker gap unresolved. The blocker check fails CLOSED: (open), tbd, pending — quoted or not — all count as unresolved.

THE CLI PATH
1cvg intent --draftprogress check while drafting
2cvg intentthe Pass 1 exit contract
ALTITUDE GUARD

Stack names leak downward: a tech choice in the spec is Pass 2's altitude and draws a WARN, bucketed by domain. An R-n with no number, unit, or comparator draws another.

03 · THE PASSES — STRUCTURE
2

Structure — record what is, as ADRs.

SKILL · tech-req-to-adrs GATE · CHECK_ADR=OK LANES · NORMAL + FULL IN · TECH-SPEC + THE REAL REPO OUT · docs/adrs/ + CONTEXT.md
WHAT YOU DO

Run the real system, don't read about it. Reconcile the spec against the terrain and record each grounding fact as a numbered ADR. Three-condition worthiness test: hard to reverse · downstream passes stand on it · it could plausibly have been otherwise. Fails the test → a glossary line, not a numbered file.

WHAT THE GATE PROVES

The decision set is canonical and consistent: 0000-context.md present, every section filled, supersede links bidirectional — and under --final, nothing still proposed.

THE CLI PATH
1scaffold-adr.sh "<slug>"auto-numbered, dated scaffold
2scaffold-adr.sh --supersede NNNNreplace, never edit
3cvg structurethe ADR gate
4cvg structure --finalnothing left proposed
NO-DRIFT

A build-verb in any ADR fails the gate — build, create, implement, add. ADRs record what is, never what to build. That single invariant is this pass's one failure mode.

## Evidence — the observation AND the runnable command that re-proves it

## Consequences — always ends with "Re-verify when: …"
ACCEPTED = IMMUTABLE
--supersede NNNN

An accepted ADR is never edited — it is superseded, stamping supersedes: / superseded_by: on both files. The gate verifies the links point at each other.

Decompose — cut the system at its real seams.

SKILL · reqs-to-swimlane-plans GATE · CHECK_PLAN=OK LANES · FULL IN · ADRs + IN-SESSION UNDERSTANDING OUT · swimlanes/<seam>/
WHAT YOU DO

The decomposition chain: seam → swimlane → leg → (task-spec, at Pass 5). A seam is the joint; a lane gets one lean PRD; a leg is the lane's named stretch — one responsibility, one proving test, yielding 1:N task-specs later. Plan altitude only: no query bodies, no handler bodies, no evals.

FIVE HARDENING RULES

H1 exactly one steel-thread lane (thread=yes — the walking skeleton) · H2 spike the riskiest seam first · H3 one owner per seam (Conway) · H4 seam evolution declared per consumer · H5 no unbroken dependency cycles.

A green check proves legs exist, are named, and are ordered — whether they are well-cut is Pass 4's judgment, not a grep's.

03 · THE PASSES — CONSENSUS · THE BARRIER
4

Consensus — a different family attacks the plan.

SKILL · sketch-plans-adversarial-review GATE · CHECK_CONSENSUS=OK + OWNER SIGN-OFF LANES · FULL IN · SWIMLANE TREE + ADRs OUT · SHARPENED PLANS + LOG
WHAT HAPPENS

A model from a different vendor family (author Claude → adversary Codex, Kimi, or Gemini) attacks the plans default-to-refuted: the 5–7 highest-leverage objections, ranked by build-time damage. Hunting grounds: unverified assumptions about existing state · build order · cross-lane interfaces. Empirical disputes get a throwaway prototype, not more prose.

THE OBJECTION LIFECYCLE

Every objection ends in exactly one of FIX (plan revised in place) or ACCEPT (recorded risk + named owner + reason to proceed). Nothing is silently dropped — the gate greps one resolution per objection. The plans are sharpened in place: the diff is the record; no new files, no new scope.

THE CLI PATH
1cvg doctor≥2 engines, ≥1 cross-family
2cvg review --adversary codex,kimimerged, referee-stamped log
3cvg review --resolve C7 --fixrecord the owner's decision
4cvg review --checkprovenance re-hashed
UNSIGNED = STOP

Gate green but nobody signed → STOP. Never cut task-specs on an unsigned plan. The owner signs “this is the right thing to build, and I am handing it to the machine” — not “the code will be correct”. That's the eval's job.

swimlanes/.consensus/objection-log.json ANATOMY OF THE OBJECTION LOG
"provenance": { engine: codex, family: openai, inputs: [sha256…, sha256…] }
// the stamp is the proof — the gate re-hashes the live plans;
// drift since review, or a same-family stamp, fails the gate
"objections": [
  { id: C2, target: swimlane-alerts-pipeline-leg-03, rank: 1,
    finding: "consumer needs event_id — producer never emits it",
    resolution: FIX — leg-02 contract amended },
  { id: C5, resolution: ACCEPT — owner: luan, risk recorded } ]
"fork": { choice: "B" } — frozen compatibility token, echoed atop every PRD
WHY CROSS-FAMILY
self-review under-reports

Self-preference bias is family-correlated: a model reviewing its own family's plan blesses too much. A fresh same-family session is the explicitly weaker fallback.

SCOPE IS FROZEN HERE
new requirement = drift

A new requirement appearing during review is logged and pushed back up the chain — never added as scope. The barrier sharpens; it does not grow.

5

Tasking — the cornerstone.

SKILL · task-spec GATE TOKEN · TIER=1 LANES · FAST + NORMAL + FULL UPSTREAM · P4 CONSENSUS DOWNSTREAM · P6 REGISTER / P7 BIND
WHAT YOU DO

Author Task-Specs from the signed plan: evals first, then the effort budget, then the HMAC seal. Each spec is atomic, sized on the six-tier scale, and carries its own definition of done.

WHAT THE GATE PROVES

Each spec is atomic, sized, and safe to delegate — the sign-off answers VERDICT: DELEGATE and stamps the seal. From that byte on, editing an eval breaks the seal.

THE CLI PATH
1cvg tasks planread-only preview + rationale
2cvg tasks new <slug> <effort>scaffold — evals first
3cvg tasks validate <spec>structure + sizing gate
4cvg tasks gate --stamp <spec>verdict + HMAC seal
5cvg eval <spec>run the spec's evals
SEAL=BROKEN

If anyone — agent or human — edits an eval after signing, the seal breaks and the gate refuses. Hand-stamping is rejected; the only path to autonomy is through the gate.

03 · THE PASSES — TASKING · SIZING

The six-tier engine. Size is a budget the gate enforces, not a guess.

Four runnable leaves and two decomposition nodes. Only the write-surface budget is gate-enforced; reads and eval counts are authoring guidance. Breach the budget and the verdict is your decomposition was too coarse.

XS
≤ 1 write path
≤ 2 files read · 1 eval
mechanical, tightly specced
S
≤ 2 write paths
≤ 4 files read · 1–2 evals
M
≤ 3 write paths
≤ 6 files read · 2–3 evals
L
≤ 5 write paths
≤ 10 files · ≤ 4 evals
ONE coherent goal
XL
node — children: ≥ 2
never runnable
dispatch the children
XXL
node — children: ≥ 3
never runnable
no route out
TWO SHAPE RULES FOR EVERY ATOM

Cut tracer bullets, not layers — a vertical slice through schema → transform → serving → test beats a horizontal “all the models”. And size to one fresh context window: spec + cited ADRs + touched files + working diff, verifying as one PR. The one exception: wide refactors sequence as expand → migrate → contract.

SEVERITY-SCALED CONFIDENCE

The delegation threshold scales with what breaks if the spec is wrong: cosmetic 0.80 · refactor 0.85 · feature 0.90 · bugfix 0.95 (the default) · security 0.98 · financial-critical 0.99.

STUB-RESISTANCE

An eval that only asserts a file exists is satisfied by echo "# assert" > x.py — the gate blocks existence-only evals. Assert the outcome: a row in a table, a role in the cluster, a revoked privilege.

HOLES ARE FIRST-CLASS

An unresolved question makes the spec status: blocked with a blocked_reason: and a non-empty Open Questions zone — and a blocked atom never reaches the gate. Ambiguity is recorded, not smuggled.

BACKLOG-WIDE LINTING

cvg lint checks cycles and overlaps across every spec — needs bash 4+ (stock macOS 3.2 prints LINT=UNSUPPORTED, exit 3; brew install bash and it re-execs itself).

Register — the board that cannot lie.

SKILL · task-specs-to-issues GATE · CHECK_REGISTER=OK OPT-IN · ALL LANES IN · SIGNED SPECS OUT · LINEAR / GITHUB / JIRA ISSUES
WHAT IT DOES

Idempotently projects each signed_off: true spec onto exactly one tracker issue — never fan out, never merge — and mirrors every depends_on edge as the tracker's own blocked-by relation. The ready frontier renders natively in the board UI.

THE SIX-VERB ADAPTER

Every tracker is one adapter file speaking six verbs: preflight · upsert · link · list-ready · list-issues · write-result. The loop uses only two; registration uses two; the parity gate reads one. A no-network fake adapter proves the whole suite offline — 145 checks.

THE CLI PATH
1cvg setup tracker linearkey → OS keychain, never argv
2cvg register --dry-rundetects cycles before any write
3cvg registerspecs → issues, 1:1
4cvg register --checkparity · DAG · no orphans
CYCLE = REFUSE ALL

A depends_on cycle refuses the whole run — it's a spec bug, not a board state. A failed preflight stops rather than half-registering.

linear issue CVG-23 ⇄ cvg/tasks/T-20260730-add-health-endpoint.md ANATOMY OF THE MAPPING
title: the spec's title, verbatim
body: goal + touches_paths + the Exit Check, verbatim — the issue carries its own proof
key: <!-- task-spec: T-20260730-add-health-endpoint --> — the marker IS the idempotency key
deps: blocked-by ⇄ depends_on, edge for edge

         the HMAC seal covers id + body + authz — the receipt never breaks it
THE ONE RULE THAT KEEPS IT HONEST
only a green eval closes an issue

Only the loop writes result state. Humans and agents can look at the board; only settlement moves it — which is why the board never lies.

PARITY, GATED

Count mismatch, orphan issue, double-registered spec, or a missing blocked-by edge — each one fails CHECK_REGISTER.

THE CAPABILITY EPOCH

Authority is granted against one signed revision: epoch = <task-id>@<spec-sha12>, scoped to the spec's own paths, and revoked on settle, block, budget exhaustion, or epoch change — closing the hole where session permissions outlive the task.

PREVENT / DETECT / CANNOT-HONOR

Each runtime adapter declares, per capability, whether it prevents the violation (kernel primitive or pre-tool hook), only detects it (portable postflight), or cannot honor it. A required control the runtime cannot enforce fails the gate closed — waive only explicitly with --accept-unenforced, written into the profile.

THE CLI PATH

2cvg bind --task <spec>freeze profile + brief + adapters
3cvg bind --check --task <spec>read-only freshness recheck
4cvg gate --path <p>ask the repo fence about one path
NEVER UPGRADED

A profile never upgrades detect to prevent because the vendor has an optional hook. Declared assurance must match what the resolver proves.

+ AGENTS.task.md — the brief pins IDENTIFIERS, never content:
"done is the Exit Check exiting zero — not your judgement."
THE FENCE IS CHECKED TWICE
per-candidate + whole-diff

Pre-write, per candidate path (vendor hook); and pre-settlement, over the whole diff — mandatory even when a stronger sandbox exists.

The Loop — attempt → verify → repeat, with brakes.

SKILL · task-loop GATE · TASK_LOOP=SETTLED LANES · ALL IN · ONE ISSUE + BOUND CONTRACT OUT · PR + RECEIPT, OR AN HONEST FAILURE
WHY IT'S A LOOP AND NOT A GATE

Each attempt is a fresh process — state lives on disk, never in a growing conversation (a retry otherwise re-reads every prior failure at quadratic cost). Brakes are checked before each engine call, where the money isn't spent yet. Budget flags can only tighten: a loop whose ceiling can be raised at the call site has no ceiling.

RED TWICE, SAME WAY → DIAGNOSE

Stop patching, start diagnosing: reproduce minimally → hypothesize in one sentence → verify the hypothesis before writing the fix → fix once, re-run. A fix applied to a confirmed cause converges in one iteration; a fix applied to a guess converges by accident.

THE CLI PATH
1cvg loop --estimate --issue <id>read-only budget preflight
2cvg loop --issue <id> --agent codexthe bounded descent
3touch cvg/loop/<id>/STOPcancel at the next brake check
4cvg loop --issue <id> --resumecontinue from the checkpoint
NEVER git add -A

Settlement stages only the contract's fs.write scope — git diff never lists untracked files, so a blanket add could smuggle an out-of-scope file unseen. Every staged path is re-checked before commit.

cvg/loop/T-20260730-add-health-endpoint/ ANATOMY OF A RUN

brief-003.md — spec path · contract · attempt 3 of 15 · only the failing checks,
   plus "what the previous attempt did (do not repeat it)"
attempts/003.log — engine transcript + verify output, one file per attempt
HANDOFF.md — why it stopped · budgets used · last failure · how to resume
STOP — touch to cancel; honored at the next brake check, then deleted
── settlement ── branch task/<id>-<slug> · scoped staging · receipt written LAST
…/cvg/STATE.md — append-only board: | when | task | engine | state | iters |
ENGINES ARE ONE FILE EACH
engines/<name>.sh — two calls

--available and --prompt-file F --workdir D. Adding an engine is a new file, never a kernel change. A pure-bash watchdog caps every attempt's wall-clock (exit 124).

UPSTREAM GAPS STAY UPSTREAM
broken eval = Pass 5 fix

Broken eval bash, a missing ADR, a stale profile — each is a named upstream gap. The loop reports BLOCKED; it never hacks the eval.

03 · THE PASSES — THE LOOP · STATE MACHINE

Eight ways a loop can land. All of them named, only three exit zero.

THE EIGHT TERMINAL STATES
SETTLEDexit 0

green evals, external writes permitted, PR opened

LOCAL_SETTLEDexit 0

green evals; policy denies external writes — local commit

NO_OPexit 0

already green on arrival — nothing to do, honestly said

BLOCKEDexit 1

needs a human, an upstream input, or tier-2 REFUTED

STALLEDexit 1

the same check failed the same way 3 times — believe it

EXHAUSTEDexit 1

a budget ceiling hit — WIP committed, HANDOFF.md written

CANCELLEDexit 3

the STOP file arrived; honored at the next brake check

ERRORexit 4

the loop itself could not continue safely

THREE BUDGET AXES — FLAGS ONLY TIGHTEN

iterations budget_iterations, default 15 · wall-clock timeout_minutes, default 90 (accumulated working time, so a resumed run isn't pre-exhausted) · tokens budget_tokens, unenforced unless declared — absence is “unknown”, never zero.

THE STAGNATION FINGERPRINT

sha256 over the [fail]/[pass] lines + the Exit Check line, durations stripped — the same failure taking 1s instead of 0s must not read as progress. Identical fingerprint = a strike; three strikes = STALLED.

04 · THE TRUST CHAIN — SEALS, TIERS & RECEIPTS

The trust chain. From a 256-bit key to a receipt that can't lie.

the seal, end to end HMAC-SHA256 v2
① provision  cvg setup signing — 256-bit key at .git/info/, mode 0600, never enters git
② stamp     cvg tasks gate --stamp — seals the canonical payload:
    id · body_digest · authz_digest (paths, deps, effort, budgets) · signed_off fields
③ verify    recomputed at validate · bind --check · accept · receipt --post-hoc
④ survive   Pass 6's tracker_ref stamp touches metadata only — the seal holds
⑤ break     one eval byte changes → DO NOT DELEGATE: modified after stamping
THE THREE-RUNG TRUST LADDER

Tier 1 — key present, MAC verifies → full crypto trust, unsupervised crank OK · Tier 2 — key or signature absent → structural-only, supervised dispatch only · Tier 3 — MAC mismatch → hard fail. Honest threat model: symmetric HMAC is tamper-evident, not tamper-proof — it binds “a repo-key holder stamped this”, and per-author signatures (Ed25519/DSSE) are the named upgrade.

RECEIPTS — A HASH CHAIN, WRITTEN LAST

cvg/receipts/<task-id>.json (cvg.execution-receipt.v1) pins the spec sha256, the profile sha256, the eval output digest, agent, and branch. A superseded receipt is archived as .attempt-<sha12-of-its-own-bytes> — and the pass receipt is written last, so it can never attest to a settlement that didn't happen.

TIER-2 VERIFICATION — THE HOLDOUT

The spec may carry a ## Holdout section: assertions excluded from the worker's brief, reserved for the judge — train/test separation borrowed from ML. cvg verify sends the diff, the stated intent, and the holdout to a different-family model prompted to refute. It never sees the worker's transcript.

BLAST RADIUS IS COMPUTED, NOT CLAIMED

High if any touched path matches auth · session · token · secret · payment · billing · migration · schema, or effort ≥ L, or the change spans > 5 files. Low + UNAVAILABLE → recorded and permitted. High + UNAVAILABLE → blocked, with three exits: a second engine, a smaller change, or an explicit --accept-unverified.

THE FULL CHAIN, IN TOKENS
$ cvg tasks gate --stamp …  → VERDICT: DELEGATE · TIER=1
$ cvg bind --check --task … → CHECK_RUNTIME_CONTRACT=PASS
$ cvg loop --issue …        → TASK_LOOP=SETTLED
$ cvg verify --task …       → CHECK_VERIFY=UPHELD
$ cvg register --check       → CHECK_REGISTER=OK
The invariant: policy is not part of the signed payload — re-signing a spec can never buy access the fence denies, and hand-stamping is rejected. The only path to autonomy is through the gate.

After any pass closes: every component, the decision it encodes, what breaks downstream without it, plus check-yourself questions. --immutable proves teaching changed nothing it taught. Optional — never blocks the descent. CHECK_LESSON=PASS

skill-creator

Author and validate new skills. Its quick_validate.py is the bar every shipped skill passes — and the same check the installer runs before it reports INSTALL=OK.

06 · THE REFEREE CLI — THE AGENT PROTOCOL

Agent-native by design. The whole surface, one JSON call.

cvg agent-context — THE SELF-DESCRIPTION MANIFEST
{
  "schema_version": "1.0",  "tool": "cvg",  "role": "referee",
  "contracts":    { stdout, stderr, token, color, determinism, resolution },
  "global_flags": [ {flag, position, effect} … ],
  "exit_codes":   [ {code, name, meaning, retryable, side_effects} … ],
  "commands":     [ {name, converge_pass, wraps, emits_tokens,
                     mutating, example, description} … ]
}
--json — THE UNIFORM RESPONSE ENVELOPE, ANY COMMAND
{ ok, command, token, verdict, exit_code, changed, dry_run,
  data, error, warnings, meta{schema_version, tool, cvg_version} }

# a pure re-invoke wrapper — the byte-parity default path is untouched;
# the underlying exit code is preserved. Proven 14/14.
--dry-run — PREVIEW WITHOUT PERFORMING

Applies to mutating commands only (review --adversary, bind, tasks gate --stamp, transition, register, setup writes). Reports the intended action, changes nothing: changed=false · dry_run=true · DRY_RUN=OK. Read-only verification has its own doors: tasks validate --no-state, bind --check, register --check.

SETUP — CHOICES, NEVER CREDENTIALS

cvg setup is a readiness board ending in SETUP=READY with your exact next step. setup key reads the tracker key from stdin, never argv, and stores it once outside the repo. setup harness scaffolds a ~50-line project router and stops — cvg never generates doctrine.

WHY AGENTS DON'T MEMORIZE THE SEQUENCE

cvg next names the current pass, its steering prompt, and its closing gate — derived from evidence. cvg ready answers “what now?” between tasks — the dispatchable frontier only (ready and unblocked), failing closed on a dangling or cyclic edge.

07 · ARCHITECTURE — CONTROL PLANE & THE WRITE FENCE

The control plane. Two tracked files answer “may ANY task ever write here?”

.cvg/gate.yaml — tracked, reviewed like any other file THE REPO WRITE FENCE
version: 2
protected_paths: # the fence a Task-Spec cannot widen
  **/.git/** · **/.cvg/** · **/.env · **/secrets/** · **/credentials/**
  **/*_key* · **/*_secret* · **/id_rsa* · **/.terraform/**
  **/migrations/** · **/auth/** · **/payments/** · **/billing/**
  .cvg/gate.yaml · bin/cvg · skills/task-*/scripts/** · .github/workflows/**
  # "an agent that edits its own verifier is the specification-gaming failure mode"
max_changed_files: 12 # blast radius, orthogonal to paths
ASK THE FENCE — READ-ONLY, ANY TIME
$ cvg gate --path src/api/health.py
  allowed  src/api/health.py
$ cvg gate --path auth/tokens.py
  REFUSED  auth/tokens.py  (rule: **/auth/**)
CHECK_GATE=OK|ABSENT|FORBIDDEN|ERROR
PRECEDENCE — THE FENCE ALWAYS WINS

The Pass 7 contract answers “may this task write here?”; the fence answers “may any task ever write here?”. Protected paths beat contract, always — and policy is not part of the signed payload, so re-signing a spec cannot buy access.

THE WORKSPACE TREE

cvg/ is the factory floor: docs/{brd,tech-spec,no-go,adrs,lessons} · swimlanes/ · tasks/ · execution/ · loop/ · receipts/ · brain/. Paths resolve against the workspace, never the git root — cvg/ may live in a subproject.

WHAT LIVES WHERE

.cvg/gate.yaml — tracked fence · .cvg/config — choices, never credentials · .cvg/identity — tracker identity map, mode 0600 · .git/info/taskspec-signing-key — the HMAC key, 0600, never enters git · tracker API keys — the OS keychain.

ENGINES AUTHENTICATE THEMSELVES

The referee holds zero model credentials. Engine CLIs (claude, codex, kimi, grok) are needed only by the passes that dispatch — each brings its own auth.

08 · OPERATING THE FACTORY — STEERING FROM CHAT

You steer in plain language. The agent drives the gates.

you
I want a storm-alerts feed for our customers. Start a Converge run — capture it.
agent
Pass 0 (idea-to-brd): drafting the BRD, grilling the gaps out of the idea… CHECK_BRD=PASS — the brief is signed.
you
Take it to requirements and architecture.
agent
Pass 1: CHECK_TECH_SPEC=PASS. Pass 2: five ADRs recorded — CHECK_ADR=OK.
you
Break it down, then have Codex attack the plan.
agent
Pass 3: two swimlanes, six legs — CHECK_PLAN=OK. Pass 4: codex raised 3 objections. Two resolved; one needs your call.
you
Objection two is right — merge the retry logic into one leg. Then sign.
agent
Plan amended. CHECK_CONSENSUS=OK — the barrier is behind us.
you
Cut the tasks, put them on the board, and ship the first ready one.
agent
Pass 5: six Task-Specs, evals first, all TIER=1 and sealed. Pass 6: CHECK_REGISTER=OK. Pass 7: CHECK_RUNTIME_CONTRACT=PASS. Pass 8: attempt → verify → repeat… green on iteration 2. TASK_LOOP=SETTLED — PR opened, receipt written. Next ready task: 2 of 6.
THE DIVISION OF LABOR

You own intent and judgment; the factory owns procedure and proof. Your voice is needed at exactly the moments that deserve it: the barrier sign-off after the adversarial review, and any objection the machines cannot settle. Everything else runs on gates.

WHY THIS WORKS

The skills are installed in your harness, and cvg agent-context hands any agent the whole surface as one JSON manifest. You never memorize the sequence — cvg next derives it, cvg lane routes it, cvg setup names the exact missing step, cvg ready answers “what now?”.

SWAP THE ENGINE, KEEP THE GATES

--agent claude → codex → kimi: the same signed spec dispatches to any of them, and the gate that scores the work is identical. Engines are one adapter file each.
