The Unit That
Verifies Itself.

Every AI coding tool consumes some form of "task." Most of those are PRDs — written for humans, interpreted by humans, judged by humans. That makes agents non-autonomous: they need a person in the middle of the loop. Task-Spec fixes that. Each spec carries its own runnable bash success criteria, so an agent reads it, executes, runs the evals, and loops on failure without a human in the middle. This is Eval-Driven Development — the same conceptual leap as TDD or Infrastructure-as-Code.

Task-Spec · the cornerstone unit · v3.6

Why the unit had to change

From "a document a human judges" to "a file that judges itself"

A PRD is a request for interpretation. It describes an outcome in prose and leaves the question of whether the outcome was achieved to a reviewer. That is a perfectly good contract between two humans — and a broken one between a human and a machine, because the machine cannot execute a standard it cannot read, and cannot know when to stop.

Task-Spec inverts the contract. The definition of done travels inside the file, as bash. That single move changes four things at once:

DimensionProse task (PRD)Task-Spec (EDD)
"Done" is decided byhuman reviewbash evals returning 0
Iteration cadencehours – daysseconds – minutes
Portabilityvendor-specificuniversal — markdown + YAML + bash
Audit trailnarrativemachine ledger
Catches ambiguitymaybeyes — the eval fails to be writable
Authoring costfaster (prose)slower — evals are harder to write
The honest cost

That last row is real and is not hidden. Writing a runnable eval is harder than writing a paragraph, and the difficulty is the point: if you cannot express done as a check, you have not finished thinking. The cost is paid once, by the author, instead of every time, by a reviewer.

The rule that makes the whole method work

No eval, not a task yet. A spec without a runnable check is a wish. Because the eval — and not the agent — defines done, any coding agent becomes a swappable commodity slot: swap Claude for Codex for Kimi and the gate is unmoved.

Anatomy — frontmatter plus six zones

Everything the executor needs, and nothing it must guess

ZoneNameWhat it holds · why
1IntentWhy this task exists — goal + bounded context. Keep it short; a Context over ~100 lines means you wrote a PRD.
2BehaviorGIVEN / WHEN / THEN statements, each labelled B-N. Every behavior demands at least one eval — this is the traceability spine.
3Contract
THE MOAT		Runnable bash eval_N() functions + the Validation Card (YAML) + the Exit Check. This is the self-verifying core.
4GuardrailsAnti-patterns and do-not-touch paths — bound the agent's blast radius, specifically. "Be careful" is not a guardrail.
5OperationsOpen questions — admit unknowns honestly so a stalled loop knows where to ask.
6Rollback + Observability
full profile only		How to reverse a failed execution, and what to watch during and after it.
Profiles — zones scale with effort

Not every task earns every zone. A minimal spec carries the load-bearing zones only; the full profile adds Rollback + Observability. The profile is effort-scaled, so an XS config bump does not have to carry a rollback plan it will never use.

Frontmatter — the machine-readable header

---
id: T-20260519-add-health-endpoint     # T-YYYYMMDD-<kebab-slug>
status: ready                            # ready|in-progress|blocked|done|parked
format_version: 3
profile: standard                        # minimal | standard | full
effort: S                                # XS·S·M·L leaf | XL·XXL node
budget_iterations: 10                    # the retry ceiling — not a success criterion
execution_backend: any                    # OPEN STRING — the backend names itself
depends_on: []                            # the DAG edges — cycle-checked
touches_paths: [src/api/server.py, tests/test_health.py]   # blast radius
tracker_ref: (none)                       # receipt written BACK by Pass 6 — never by hand
signed_off: false                         # only the PRE gate flips this
accepted: false                           # only the POST gate flips this
---
Two fields no human may write

signed_off and accepted are gate outputs, not author inputs. Hand-stamping either is rejected — the sign-off envelope check recomputes an HMAC over a canonical payload and compares. tracker_ref is likewise a receipt, written back by Register after a successful upsert.

Task-Spec · the cornerstone unit · v3.6

A complete spec, end to end

~95 lines · every behavior eval-covered · every eval traced to a behavior

## Behavior
- B-1 — GIVEN the api server is running WHEN a client GETs /health
        THEN it responds HTTP 200 with body {"status":"ok"}
- B-2 — GIVEN the new endpoint exists WHEN the test suite runs
        THEN a regression test for /health passes

## Success Criteria          # THE MOAT — runnable, deterministic
```bash
eval_1() { uvicorn src.api.server:app --port 8001 & PID=$!; sleep 2; kill -0 $PID 2>/dev/null; }
eval_2() { curl -fs http://localhost:8001/health | jq -e '.status == "ok"'; }
eval_3() { pytest tests/test_health.py -q; }
```

## Validation Card          # the machine-readable index of the evals
```yaml
success_criteria:
  - {id: eval_1, verifies: [B-1], check_type: deterministic, terminal: true}
  - {id: eval_2, verifies: [B-1], check_type: deterministic, terminal: true}
  - {id: eval_3, verifies: [B-2], check_type: deterministic, terminal: true}

retry_policy:
  max_iterations: 10
  circuit_breaker_no_progress: 3
  on_terminal_failure: park_with_context

agent_contract:
  version: 2
  required_tools: [git, bash, python3]
  emit: [pass, fail, retry_with_reason, parked_with_context]
```

## Exit Check
```bash
eval_1 && eval_2 && eval_3
```
Traceability

Both directions

B-1 is covered by eval_1 + eval_2; B-2 by eval_3. Every behavior has an eval and every eval names a behavior — an untraced behavior FAILS the Definition of Done.

The circuit breaker

Stop patching

circuit_breaker_no_progress: 3 ends the "try the same thing louder" failure mode; on terminal failure the task parks with context rather than looping or silently dying.

The six-tier engine — leaves run, nodes decompose

v3.4 made the cut recursive · size by context, verification, and blast radius

Sizing is agent-native: not human hours, but how much context the unit needs, how it verifies, and how wide it writes. Two kinds. Leaves (XS/S/M/L) are directly runnable atoms that fit one fresh executor session. Nodes (XL/XXL) are decomposition directives — not runnable at all; they MUST declare a children: block and expand into leaves.

SizeKindWrite-surface budgetExample
XSleaf≤ 1 patha config key; bump a dependency
Sleaf≤ 2 pathsa /health endpoint + its test
Mleaf≤ 3 pathsa dbt model + schema + test
Lleaf · the ceiling≤ 5 paths · long-horizon backenda service slice as ONE coherent goal
XLnode · decomposeschildren ≥ 2 · owns nonea whole swimlane → its leg leaves
XXLnode · decomposeschildren ≥ 3 · owns nonea whole backbone → swimlane nodes

Fig 1 Descend by decomposition, run only leaves, compose verified results back up. A breached write-surface budget is a signal that the decomposition was too coarse — split further.

The gate is enforcement, not advice

A leaf over its budget WARNs "mis-sized — split or reclassify UP." An XL/XXL node with too few children FAILs "must decompose — no route out." And safe-to-delegate refuses to delegate a node at all — a worker dispatches a node's children, never the node itself.

Task-Spec · the cornerstone unit · v3.6

Recursion, not escalation

v3.4 removed the SDD escape · v3.6 removed the vendor lock

Task-Spec used to have an exit. The old effort gate routed XL → SDD: work above a size threshold left the format entirely for a plan-driven paradigm (AgentSpec / OpenSpec / Spec Kit). v3.4 removed that route. Big work now decomposes in — the same format, self-similar at every scale — rather than escalating out.

  NEW["v3.4 + v3.6 — one path

  classDef old fill:#12283f,stroke:#3a5670,color:#8fa6ba;
  classDef new fill:#0f3a26,stroke:#47b87c,color:#dff0e6;

The argument for the change is empirical: frontier engines execute well-scoped atoms reliably, and a tree of verified atoms composes back up more safely than one monolithic spec. A monolith hides which step regressed and makes per-stage evals unenforceable. Decomposition keeps every defect behind its own green check.

v3.6 — the L tier stops naming a vendor

Until v3.6, effort: L hard-failed unless execution_backend: glm. That contradicted the format's own rule that execution_backend is an open string — "the backend names itself; the values are non-normative examples, not an allow-list." The gate's real intent was an L leaf needs a long-horizon builder, not an L leaf needs one specific vendor.

# the gate now checks membership, not identity
TS_LONG_HORIZON_BACKENDS="${TASKSPEC_LONG_HORIZON_BACKENDS:-glm claude codex kimi}"

# override per fleet — your harness names itself
export TASKSPEC_LONG_HORIZON_BACKENDS="claude codex kimi glm my-harness"
Why this matters beyond one flag

It was surfaced by a real user whose fleet is Claude Code / Codex / Kimi: an L-sized spec could not name the engine that was actually going to run it. A format that claims vendor-neutrality has to mean it at the gate, not just in the prose — otherwise the neutrality is decorative.

The two gates are duals

Same evals · opposite expectations · one certifies the spec, the other the work

This is the most misunderstood part of the format. There are two gates, they run the same evals, and they expect opposite results. The PRE gate certifies that the spec is safe to hand to a machine. The POST gate certifies that the work actually satisfied it.

A spec is dispatchable when, and only when, the PRE gate returns VERDICT: DELEGATE. There is no other path — hand-editing signed_off is caught by the envelope check.

Task-Spec · the cornerstone unit · v3.6

Anti-reward-hacking — why a green eval means something

The acceptance gate assumes the executor may be wrong, or optimising for the wrong thing

An eval-defined "done" is only as trustworthy as its resistance to being gamed. A sufficiently motivated optimiser can satisfy a check without satisfying the intent: weaken the assertion, widen the blast radius, or write a test that would have passed anyway. The POST gate is built on the assumption that this will happen, and each layer closes one route.

LayerWhat it closes
Re-run, never trustThe gate runs the evals itself, from a clean checkout — it never accepts the executor's report of its own success. A non-zero exit is rejected automatically.
Blast-radius checkEvery changed file must be inside touches_paths ∪ creates_paths. "I fixed it by editing the test harness" is caught here.
HMAC contract integrityThe envelope seals the eval bodies at sign-off. If the evals were weakened after the spec was signed, the recomputed signature no longer matches and acceptance fails.
--gold-sanityThe Goodhart guard: the eval must FAIL on the unpatched baseline. An eval that passes without the change proves nothing — it was never discriminating.
Atomic state machineAdvisory lock, validated transition, tmp-file + atomic move. Two executors cannot both claim one ready task.
Append-only ledger_metrics.jsonl is forensic and append-only; _state.yaml is a derived, rebuildable index. The frontmatter is the truth, so the index cannot silently diverge.
The evals must discriminate

This principle governs the format's own test suites too: every gate ships with regression fixtures that prove the negatives fail. A fixture that wrongly PASSes on a previous version is treated as a defect in the gate. A check that cannot fail is not a check.

Conformance — what "this engine can run it" means

Three cumulative levels · certified by a real suite, not a claim

"Vendor-portable" is a testable property, not a marketing line. An executor earns a level by driving reference specs to a defined outcome — the suite ships in the skill, and scripts/ref-executor.sh is an L2-conformant reference implementation.

LevelWhat it addsHow it's certified
L0Read the format and run the evals — given a signed spec, produce work that makes the Exit Check return 0.Drives a solvable reference spec; the runner exits 0.
L1L0 + honor the lifecycle — acquire the lock (status → in-progress) before working, release it (→ done) on success.After success the spec's status is done.
L2L1 + honor the retry budget — on a spec it cannot satisfy within budget_iterations, stop and park with a reason rather than loop forever.An unsolvable reference spec ends parked, and the executor does not time out.
L0

Supervised

safe for one-shot dispatch with a human watching.

L1

Shared backlog

the lock prevents two executors double-picking the same ready task.

L2

Unattended

a runaway task self-terminates into parked instead of burning budget forever.

# certify your own executor against the suite
bash scripts/conformance-check.sh --level L2 --executor "my-runner --flags"
A plain bash loop reaches L0

That is deliberate — the floor is low enough that the format is genuinely portable. L2 is the bar for an executor you would trust to run unattended, which is the bar the dark factory actually needs.

The anti-pattern that breaks all of it

Editing T-*.md frontmatter by hand bypasses the lock and the ledger. Use transition-status.sh. Derived state can always be rebuilt with rebuild-state.sh; a corrupted authoritative state cannot.

One format, many executors

The agent contract is what makes the coding engine a commodity slot

Any agent consuming a Task-Spec honors the same contract. That contract — not a plugin, not an API — is what makes the format portable.

on_pickup:
  - read: zones 1–6
  - parse: validation_card YAML
  - acquire: lock via transition-status.sh      # L1

per_iteration:
  - execute: implementation
  - run: all success_criteria as bash
  - emit: pass | fail | retry_with_reason

on_terminal_state:
  pass:              status → done; archive
  budget_exhausted:  status → parked            # L2 — with context, never silence
ConsumerHow it reads the spec
Claude Codenative — markdown + YAML + bash
Codex CLIsame file, cross-vendor
Kimisame file — the sprinter class, atomic cranks
Gemini / Cursor / Aidersame file
anthivedispatches one session per Task-Spec
taskshipruns a 3-phase mini-SDD against each spec
A human with a terminalreads it as a checklist; runs the evals by hand
The black-box guarantee

Size → engine routing is advisory — a dispatcher heuristic keyed off effort, never an override of an author's explicit execution_backend. The agent contract keeps the executor a black box: the format specifies what must be true, never how the engine must think.

Where this sits in Converge

Task-Spec is Pass 5 · Tasking — the first pass below the barrier, and the cornerstone of the whole method. Pass 4's hardened plans decompose into these units; Pass 6 Register (opt-in) projects each signed spec onto one tracker issue; Pass 7 Bind binds a signed spec's exact hash to its runtime and emits the harness; Pass 8 The Loop drives one issue to a green-eval PR. Every one of those passes depends on the property this format provides: the definition of done travels inside the file.

The honest boundary

A green eval proves the code matches the spec. It does not prove the spec was right. Task-Spec automates the verification of the build, not the judgment of whether the build was worth making — that judgment is what Converge's Phase 1 and its adversarial Consensus pass exist to protect.
