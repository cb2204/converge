Passes, Skills
and the cvg CLI

Archived v0.1 deck · 0.2 migration annotations are not release evidence

Converge turns altitude into evidence. It moves from a product idea to a bounded runtime task through explicit artifacts, named gates, and machine-readable receipts. This guide explains every numbered pass, the skills that implement them, and the cvg CLI that keeps the chain deterministic.

These planes let the system evolve without erasing accountability. A skill can improve its interview technique without changing the Task-Spec schema. Where a change crosses those boundaries, it needs an explicit compatibility decision rather than an incidental documentation edit.

02

The complete 0–8 descent

The chain is ordered by decreasing abstraction. Optional routes remain explicit; no step silently pretends to have happened.

Pass 0 and Pass 6 are optional routes. Pass 0 is skipped when an approved BRD already exists. Pass 6 is skipped when no tracker projection is needed. Their absence must be deliberate, not accidental.

A pass check is a predicate, not a writing score. Draft flags make incomplete work explicit; final or checked modes tighten the contract. Preserve the failing token and diagnostics, update the underlying artifact, and rerun the same check. Bypassing a gate because the prose “looks close” breaks the lineage every later pass assumes.

03

Three phases and a hard barrier

Shape · 0–3

Turn ambiguity into reviewable design

Define product intent, technical requirements, architectural decisions, and independent delivery swimlanes.

Barrier · 4

Earn permission to task

Adversarial review resolves objections under machine checks; accountable owner approval remains a separate human act before tasking.

Execute · 5–8

Bind, run, and verify

Author executable tasks, optionally project them, constrain runtime authority, and loop until a named terminal state.

04

Pass 0 · Capture

0
skill · idea-to-brd

Produce an approved BRD—or a documented no-go

Capture the user, problem, desired outcome, evidence, non-goals, constraints, risks, success measures, and ownership. This is optional only when equivalent approved authority already exists.

Input

Idea, request, research, constraints, or an existing product brief.

Output

Versioned BRD with approval status or a no-go rationale that prevents wasteful descent.

Failure mode: a feature description is not a BRD. Without a user, measurable outcome, scope boundary, and decision owner, downstream artifacts only make ambiguity more expensive.
05

Pass 1 · Intent

1
skill · brd-docs-to-tech-req

Translate product authority into technical requirements

Map desired behavior into functional and non-functional requirements, integrations, constraints, observability expectations, security concerns, and acceptance anchors—without choosing every implementation detail.

Preserve

Original business outcome, non-goals, and decision boundaries.

Add

Interfaces, data, failure behavior, performance, privacy, and operating constraints.

Avoid

Invented requirements, premature task lists, and architectural choices with no rationale.

Pass 2 · Structure

2
skill · tech-req-to-adrs

Convert choices into explicit architectural decisions

Write ADRs for consequential decisions and maintain a context document that explains system boundaries, existing constraints, interfaces, and the vocabulary future passes must share.

ADR elementQuestionWhy it matters later
ContextWhat forces make a decision necessary?Stops alternatives from being judged without their constraints
DecisionWhat is chosen and where does it apply?Gives plans a stable architectural boundary
AlternativesWhat credible options were rejected?Prevents repeated debate and reveals trade-offs
ConsequencesWhat becomes easier, harder, or irreversible?Feeds risk, rollback, and validation design

07

Pass 3 · Decompose

3
skill · reqs-to-swimlane-plans

Produce independent, dependency-aware delivery plans

Split work by coherent ownership and integration boundaries. Each plan lives under cvg/sketch/swimlane-*/ and must identify entry criteria, deliverables, risks, checks, dependencies, and handoffs.

A swimlane is not a team name. It is a unit of planning that can advance independently until an explicit synchronization point. Good lanes reduce contention without hiding integration work.
08

Pass 4 · Consensus barrier

4
skill · sketch-plans-adversarial-review

Challenge the plan before task generation

Reviewers attack assumptions, missing dependencies, verification gaps, sequencing, rollback, and ownership. The barrier opens only after objections are dispositioned and an owner signs off.

Generate objections.

Seek failure conditions, not stylistic preferences.

Record a permitted disposition.

Use FIX to change the plan or ACCEPT with a named owner. REJECT and “noted” do not pass.

Harden plans.

Update the underlying swimlanes; an objection log alone does not improve the plan.

Authorize tasking separately.

CHECK_CONSENSUS proves machine conditions and current hashes. A human owner must still accept residual risk before Pass 5.

Snapshot and authority boundaries. Review dispatch overwrites the current .consensus/objection-log.json; it is a replaceable reviewed snapshot, not an append-only ledger. Preserve prior states in Git or an explicit archive. The gate cannot verify the separate human owner-approval act.
09

Pass 5 · Tasking

5
skill · task-spec

Compile plans into a signed executable DAG

Each Task-Spec binds behavior, success criteria, evals, allowed paths, dependencies, effort tier, executor requirements, budgets, and lifecycle state. Unattended work requires Tier 1 keyed integrity.

Before execution · PRE

cvg tasks gate <spec> returns a delegation verdict without Task-Spec or Converge metadata writes, but still executes declared eval code. --stamp is mutating: a re-seal retires the old signature before validation, then writes a fresh envelope only on pass; failure may leave the spec cryptographically unsealed.

After execution · POST

cvg tasks accept <spec> returns the verdict without Task-Spec or Converge metadata writes, but still executes eval code. Default Git-backed POST inspects changed paths; --no-blast-radius or no-Git execution may accept without scope evidence. Only --stamp writes acceptance.

The release is Task-Spec v0.1.0; the data contract remains format_version: 3. Release and format versions answer different compatibility questions.
Traceability enforcement is split. PRE hard-fails unproved behaviors and dangling behavior IDs but only warns when an eval omits verifies:. cvg tasks dod is the current gate that hard-fails the missing reverse mapping.
10

Pass 6 · Register

6
skill · task-specs-to-issues · opt-in

Project canonical tasks into an external tracker

Registration creates or reconciles issues while keeping Task-Spec files canonical. Stable identifiers and backlinks let the tracker serve collaboration without becoming a second source of truth.

Canonical

Task identity, dependency DAG, scope, contract, signature, and acceptance remain in git.

Projected

Title, status, ownership, labels, summaries, and links support human coordination.

Reconciled

Idempotent mapping prevents duplicates and CHECK_REGISTER detects drift.

11

Pass 7 · Bind

7
skill · task-to-runtime-contract

Derive runtime authority without duplicating task intent

Part 7A emits task identity, a capability envelope, provider and settlement policy, portable enforcement artifacts, and a hash-bound pointer to the Task-Spec budget fields—it does not copy budget values or define credential delivery. Part 7B emits a compact task-scoped brief with identifiers plus goal, exact paths, Exit Check, runtime boundaries, assurance, and closure; secrets remain a harness/host concern.

The Manager is not Pass 7. Fleet-level scheduling and orchestration are future control-plane work outside the numbered chain. The current canonical Pass 7 is Bind.
12

Pass 8 · Loop

8
skill · task-loop

Attempt, verify, retry, and terminate truthfully

Each attempt runs in a fresh process. Before another worker attempt, the kernel checks the iteration cap, accumulated working time, and—when configured—adapter-reported worker tokens. It does not interrupt an in-flight attempt or recheck those counters before Tier 2, so the time/token brakes are pre-attempt controls rather than strict end-to-end ceilings. The loop records checkpoints, detects repeated failure signatures, reruns the sealed task eval, applies settlement path policy, and may invoke Tier 2. Auto-selection prefers a family different from the Task-Spec’s recognized execution_backend, not Loop’s actual --agent; explicit or sole judges may be same-family. Default text reports judge and strength, JSON adds independence, and Loop gates only the verdict token.

Zero exitNon-zero exitInvariant
SETTLEDBLOCKEDCandidate cannot settle under current evidence/policy: gate-only RED, Tier 2 refusal/unusable verdict, or settlement refusal
LOCAL_SETTLEDSTALLEDRepeated evidence without meaningful progress
NO_OPEXHAUSTEDA pre-attempt iteration, elapsed-work, or configured reported-token check stopped another worker launch
—CANCELLEDA STOP file was observed before another worker attempt; it does not interrupt an in-flight worker or Tier 2
—ERRORControl-plane invariant or task/contract resolution failed
Settlement evidence must be inspected. In a non-dry run, SETTLED means the branch was pushed; the settler opens a PR when gh exists and otherwise prints a manual PR body. Public Loop --dry-run performs initial setup, prints resolved controls, then exits DRY_RUN=OK before worker, eval, settlement, receipt, push, or PR; it emits no TASK_LOOP verdict. Non-dry SETTLED/LOCAL_SETTLED attempt a receipt write without revoking success when it fails.

15

What the CLI is—and is not

Current role

Local control surface and referee

cvg initializes workspaces, routes skills, validates pass artifacts, manages Task-Spec state, performs acceptance, binds runtime authority, and drives the current task loop.

Not its role

Not the model and not the future Manager

The CLI does not reason creatively or own product authority. Fleet scheduling, rich graph/board operations, and a broad delivery control plane remain future work unless a command exists in live help.

$ cvg version cvg 0.1.0 (task-spec 0.1.0) $ cvg help # Live help defines surface and syntax; source and tests define semantic boundaries.
Human mode

Concise diagnostics explain what failed, where the canonical source lives, and which safe command repairs or rechecks it.

Agent mode

cvg agent-context emits a machine-readable command tree, tokens, exit taxonomy and contracts so a model does not infer syntax from prose.

Automation mode

Stable stdout tokens and exit codes select control flow. Automation never scrapes colors or a sentence such as “looks good.”

Router, not pass. cvg lane <intent> advises FAST, NORMAL, or FULL. Sensitive or irreversible work is floored at NORMAL; a new system, service, or seam forces FULL. File count only tightens the starting result: more than 5 files upgrades FAST to NORMAL, while more than 15 upgrades an already-NORMAL result to FULL. Routing never waives the signed-spec and downstream proof gates.

17

Machine protocol: stdout, stderr, tokens, exits

A CLI used by agents must be less ambiguous than one used only by humans. Stable tokens and exit codes let harnesses branch without parsing prose.

stdout

Primary result, identifiers, machine tokens, or requested serialized data. Keep it safe to pipe.

stderr

Diagnostics, explanations, remediation, and progress that should not corrupt the primary output.

exit code

Zero means the command’s declared predicate held; non-zero means it did not or the command failed.

Token typeExamplesConsumer behavior
Pass checksCHECK_BRD, CHECK_PLAN, CHECK_CONSENSUSBlock descent on non-zero
Runtime checksCHECK_RUNTIME_CONTRACT, CHECK_VERIFYRefuse on non-zero; interpret recorded UNAVAILABLE under blast-radius/waiver policy rather than assuming every non-UPHELD token fails
Loop markerTASK_LOOPAssociate attempt events with the controller
Terminal statesSETTLED, STALLED, ERROREnd a non-dry loop and select downstream action; dry-run instead exits DRY_RUN=OK without a terminal verdict
Safe shell consumption

Capture stdout, stderr and exit status separately. Compare an exact documented token, reject an unknown value, and preserve diagnostics with the receipt. Never use a substring such as “success” or assume empty output means success.

Versioned consumption

Read cvg version or agent-context before depending on a contract. When automation and binary disagree, stop with a compatibility error; do not try a similar-looking roadmap command.

Error is never success. Successful zero-exit loop states are only SETTLED, LOCAL_SETTLED, and NO_OP. BLOCKED, STALLED, EXHAUSTED, CANCELLED, and ERROR must drive non-success control flow even when useful evidence was produced.

Operator walkthrough: idea to closed task

Initialize and inspect.

Create the cvg/ workspace, read local instructions, and confirm cvg version and live help.

Choose the honest entry pass.

Start at Pass 0 for an idea, Pass 1 for an approved BRD, or later only when equivalent canonical inputs already exist.

Run each skill and gate.

Create the artifact, review it, run the pass check, and preserve the receipt before descending.

Stop at consensus.

Resolve adversarial objections and stamp owner sign-off. Never generate tasks around an unresolved barrier.

Compile and seal tasks.

Generate Task-Specs, resolve dependencies and sizing, then run PRE stamping for unattended work.

Register only if useful.

Project canonical tasks into the tracker and verify backlinks without surrendering source-of-truth ownership.

Bind the runtime.

Hash-bind the Task-Spec, derive capabilities and policy, emit enforcement artifacts and a compact task-scoped brief; keep budget values canonical in Task-Spec and credential delivery in the harness/host.

Loop to a named state.

Launch fresh workers, rerun the sealed eval, apply settlement and holdout rules, then—only for SETTLED or LOCAL_SETTLED—confirm the attempted pass-receipt write succeeded.

Close Task-Spec separately.

Run the metadata-nonwriting POST verdict, stamp acceptance only on success, then explicitly transition to done.

$ cvg init $ cvg capture cvg/docs/brd-export.md $ cvg intent cvg/docs/tech-spec-export.md $ cvg structure --final --dir cvg/docs/adrs $ cvg decompose --dir cvg/sketch $ cvg review --adversary codex,kimi $ cvg review --check $ cvg tasks validate cvg/tasks/T-20260729-export-format.md $ cvg tasks gate --stamp cvg/tasks/T-20260729-export-format.md $ cvg bind --task cvg/tasks/T-20260729-export-format.md $ cvg loop --issue T-20260729-export-format --estimate $ cvg loop --issue T-20260729-export-format --agent codex # Pass 8 emits the terminal token and attempts the pass-receipt write; confirm the file. $ cvg tasks accept cvg/tasks/T-20260729-export-format.md $ cvg tasks accept --stamp cvg/tasks/T-20260729-export-format.md $ cvg transition T-20260729-export-format done

This sequence is illustrative, not permission to skip human decisions. External tracker setup or registration changes another system and must follow the project’s explicit write boundary. A Tier 2 judge should be genuinely different from the worker when policy requires independence. Save the exact terminal token and receipt, not only the final command transcript.

Operating rules worth memorizing

1 · Enter honestly

Choose the earliest pass whose required input is already authoritative.

2 · Never cross red

Pass 4 is a barrier. Unresolved objections stop the chain.

3 · Keep task truth local

Trackers and dashboards project Task-Spec state; they do not replace it.

4 · Separate intent and authority

Task-Spec says what done means; runtime binding says what execution may do.

5 · Keep evidence roles distinct

Loop determines TASK_LOOP; POST stamping changes acceptance. For an actual change into done, the guard checks accepted truth, non-placeholder acceptance provenance, and a matching parseable result: pass receipt; same-state done returns NOOP before that guard, which also omits receipt provenance, hashes, profile, full schema, and a source-edge matrix.

6 · Label future work

Manager and control-plane concepts stay outside the shipped 0–8 chain until implemented.
