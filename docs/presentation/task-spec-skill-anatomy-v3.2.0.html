Jump to the closed loop About the v0.8.1 refresh

Most AI-coding "tasks" are PRDs — written for humans, judged by humans, which keeps a human stuck in the middle of every agent loop. A Task-Spec carries its own runnable bash success criteria: the agent reads the spec, does the work, runs the evals, and loops on failure without supervision. Humans sit only at the edges — intent-setting (Phase 1) and acceptance review (Phase 9). Version 3.4 adds one recursive sizing model: runnable leaves at XS/S/M/L and decomposition nodes at XL/XXL. This is Eval-Driven Development (EDD).

02 The closed loop — author → gate → execute → accept

The full v3 lifecycle. The loop is closed: Phase 7 certifies the spec is delegate-safe (evals are well-formed bash; assertion failure is expected — the work isn't done yet), and Phase 9 certifies the work is real (evals now pass from a clean checkout, the change set stayed inside the blast radius, and the sign-off HMAC is intact). A task is provably DONE only when accept-task.sh writes accepted: true.

03 The nine phases, one by one

Phases 1–7 are authoring (Claude + the task-architect agent produce a stamped spec). Phase 8 hands off. Phase 9 is acceptance. A fast-batch shortcut exists for known domains: skip Phases 2 and 4 and bulk-generate stubs with batch-generate.sh.

Phase 1
Understand

Parse intent into five answers: verbal description, effort class (XS/S/M/L/XL), agent hint, source provenance, best-guess touches_paths. If vague — ask once, never proceed fuzzy.

Phase 2
Research
Context7 · Exa · Ref

MCP validation of the domain: official docs, production examples, canonical references. Findings feed the Anti-Patterns and Do-Not-Touch zones with real-world failure modes.

Phase 3
Scan

Read-only pass over the host repo: do the touches_paths exist, do in-flight tasks touch the same files, what conventions (CLAUDE.md, editorconfig) apply.

Phase 4
Architect
task-architect agent

The judgment layer. Applies the Agreement Matrix (KB + MCP), picks isolation class, drafts the 3+ evals, and returns a build plan with a confidence score. Below the severity threshold (0.80–0.99) it asks the user before composing.

Phase 5
Compose
generate-task-spec.sh

Scaffold T-*.md from the template, then fill frontmatter + all six zones. New specs are format_version: 3; legacy v0/v1/v2 files validate with warnings.

Phase 6
Validate
validate-task-spec.sh

The linter, not the gate. Structural checks only: zones present, no TODO placeholders, evals are valid bash, id matches filename, deps exist, Exit Check calls every eval, behavior↔eval traceability. Success idempotently updates _state.yaml.

Phase 7
Gate (PRE)
safe-to-delegate.sh --stamp

The only path to signed_off: true. Composes validate + eval execution into one go/no-go verdict. Evals must run without bash-level errors; assertion failure is expected. Stamps an HMAC-SHA256 envelope over the eval bodies — hand-stamping is rejected.

Phase 8
Dispatch
runbooks/dispatch-recipes/

Hand the stamped spec to the executor named by execution_backend (an open string, not an enum). Bundled recipes: claude-code, codex, kimi, gemini, taskship, anthive, custom.

Phase 9
Accept (POST)
accept-task.sh --stamp

The opposite question: is the work real? Re-runs evals from a clean checkout (must PASS), checks blast radius, re-verifies the HMAC, optional --gold-sanity Goodhart guard. Writes accepted: true — closing the loop.

04 The two gates are duals

Same evals, opposite expectations. Before the work, the evals should fail (for the right reason). After the work, the evals must pass (from a clean checkout). Everything between the gates runs without a human.

PRE-gate · safe-to-delegate.sh · Phase 7
POST-gate · accept-task.sh · Phase 9
“Are the evals well-formed enough to delegate?”
  • Structural validation must exit 0
  • Eval bodies execute with no bash-level errors — no syntax errors, unbound variables, missing commands, inverted-grep footguns
  • Assertion failure is EXPECTED — the work isn't built yet; the gate fails only for the wrong reason (broken bash)
  • Verdict: DELEGATE or DO NOT DELEGATE
stamps  signed_off: true  +  signed_off_sig (HMAC)
“Is the work REAL?”
  • Evals re-run from a clean checkout — now they must PASS
  • Blast radius: change set stays inside touches_paths, outside do-not-touch
  • HMAC re-verified: eval bodies unchanged since sign-off (nobody weakened the tests to pass them)
  • --gold-sanity: Goodhart guard — blocks an eval that also passes on the unpatched baseline
stamps  accepted: true
Honest trust claim: the HMAC envelope is tamper-evident, not tamper-proof. It proves evals weren't edited after stamping (repo-shared key, set up by configs/setup-taskspec-signing-key.sh). It's a drift/accidental-edit guard, not a security boundary. The claim is “humans at intent + review” — never “no humans.”
05 Anatomy of a T-*.md — frontmatter + six zones

Which zones are required scales with the profile field (lite / standard / full). The irreducible core — Goal, runnable Success Criteria, Exit Check — is present at every profile. Rollback + Observability are required only on full.

Frontmatter Machine-parseable metadata id, title, status, format_version: 3, profile, effort, budget_iterations, agent, depends_on, touches_paths, source_note, signed_off, accepted — plus optional severity, priority, execution_backend, requires, baseline_ref.
Zone 1 · Intent Why this task exists One-line Why + Goal + lean Context (≤100 lines, link don't duplicate). If Zone 1 outweighs the Contract you wrote a PRD, not a Task-Spec.
Zone 2 · Behavior Given / When / Then clauses standard + full B-N clauses state what the task must DO in plain language. The traceability rule: every behavior verified by ≥1 eval, every eval's verifies: [B-N] points at a declared behavior. No orphans in either direction — the validator flags both.
Zone 3 · Contract Runnable verification THE MOAT Success Criteria (≥3 bash eval_N() functions — terminal, idempotent, ordered cheap→expensive) + Validation Card (YAML mirror: retry policy, agent contract, timeouts, sandbox) + Exit Check (eval_1 && eval_2 && eval_3). Every other task format is readable; this one is executable.
Zone 4 · Guardrails What NOT to do Anti-Patterns (specific don'ts with reasons, mined from MCP research) + Do-Not-Touch (exact paths). Bounds the agent's blast radius; “be careful” is rejected — if empty, write (none) explicitly.
Zone 5 · Operations Open questions Admitted unknowns. An unresolved hole is a first-class blocker: it sets status: blocked (A2A input-required), so the spec never reaches the gate until answered. Honest specs surface ambiguity instead of hiding it.
Zone 6 · Rollback + Observability Reversal & runtime watch full profile only Rollback Plan (git revert / restore steps) + Observability Hooks (expected duration, metrics, alert conditions). Required for unattended dispatch or security / financial-critical severity.
06 The CAW Triad — Capability, Agent, Workers

The skill is the “cornerstone CAW”: a three-layer bundle where the deterministic workflow, the judgment, and the fresh knowledge live in separate places.

C
Capability — the Skill

SKILL.md + 20 bash scripts + the template. The deterministic layer: workflow phases, linter, gates, state management. Portable as a single folder — copy it to ~/.claude/skills/, run install.sh, and /task-spec works in every repo.

A
Agent — task-architect

The judgment layer, spawned in Phase 4 with isolated context. Classifies effort, applies the Agreement Matrix (KB + MCP), drafts evals and guardrails, returns a build plan with a confidence score. Installed to ~/.claude/agents/ by install.sh.

W
Workers — the MCPs

Fresh validation at authoring time: Context7 (official library docs), Exa (production examples), Ref (canonical references). Their findings ground the Anti-Patterns and Do-Not-Touch zones in real failure modes, not guesses.

agents/

Intent: portable judgment. Ships task-architect.md inside the skill folder so the whole triad travels as one directory; install.sh copies it to ~/.claude/agents/ where Claude Code can spawn it.

configs/

Intent: trust setup. One script that provisions the repo-shared HMAC signing key (with a .git/info fallback) so the sign-off envelope can be stamped and verified.

evals/

Intent: the skill grades itself. Benchmark cases proving the skill triggers on the right phrases and exercises the crown jewels (zones, traceability, effort gate, closed loop). Documents a known headless-detector limitation honestly.

references/

Intent: the knowledge base. Concepts answer “what IS X?” (format spec, EDD, zones, profiles, conformance, signed-off). Patterns answer “how do I write X?” (idempotent evals, YAML cards). Schemas make the format machine-consumable; examples prove cross-language consumption.

runbooks/

Intent: operational playbooks. Entry paths (fuzzy intent, meeting note, legacy task, batch sprint, decomposition), lifecycle ops (validating, dispatching, crash recovery), and the dispatch-recipes/ adapter layer — one recipe per engine, same five-section shape.

scripts/

Intent: the deterministic machine. Everything enforceable is a bash CLI, not prose. Core gate path (validate, safe-to-delegate, run-task-spec, _lib.sh) runs on macOS system bash 3.2 with zero setup.

templates/

Intent: one canonical scaffold. task-spec.md.tpl defines the v3 shape (frontmatter defaults, zone skeletons, {{TODO}} stubs) that generate-task-spec.sh and batch-generate.sh instantiate.

tests/

Intent: prove the machinery. Six suites (author flow e2e, HMAC envelope, extractor fuzz, bash-3.2 portability, cross-engine equivalence, v3 closed loop) + the vendored executor-conformance suite + 17 adversarial fixtures with an oracle of expected verdicts.

09 Effort gate — six tiers, two kinds, one tasking path

Version 3.4 separates runnable leaves from decomposition nodes. XS/S/M/L leaves must fit one fresh executor context and a gate-checked write-surface budget. XL/XXL nodes are composition units: they declare children and are never delegated directly.

ClassKindWrite-surface budgetGate behaviorExecution
XSleaf ≤ 1 path Smallest runnable atom; no children:. Kimi-class sprinter
Sleaf ≤ 2 paths Runnable atom; a larger surface warns to split or reclassify. Kimi-class sprinter
Mleaf ≤ 3 paths Runnable vertical slice that still fits one fresh context. Kimi-class sprinter
Lleaf ceiling ≤ 5 paths One coherent goal only; requires execution_backend: glm. GLM long-horizon builder
XLnode no runnable surface Requires at least two child Task-Spec ids. never delegated
XXLnode no runnable surface Requires at least three child Task-Spec ids. never delegated
Gate 0 is leaf-only: safe-to-delegate.sh refuses an XL/XXL node even when its structure validates. A worker dispatches the children, never the parent node. This removes the old SDD escape: tasks decompose into tasks until every executable unit is a bounded leaf.
10 Executor conformance — earning the word “conformant”

safe-to-delegate.sh certifies a spec; conformance-check.sh certifies an executor. They are duals. “Any conformant engine can pick it up” is testable, not marketing — a standard wins on its conformance suite + adapters, not its prose.

LevelThe executor must…What it buys
L0 Read the format + run the evals — make the Exit Check return 0 on a solvable spec. Safe for supervised, one-shot dispatch.
L1 L0 + honor the lifecycle — acquire the lock (status → in-progress), release on success (→ done). Safe for a shared backlog; no double-picking.
L2 L1 + honor the budget — on an unsolvable spec, stop and park with a reason instead of looping forever. Safe for unattended operation; runaway tasks self-terminate.

Status lifecycle ↔ A2A interop. The status transitions map onto the Linux Foundation A2A TaskState enum, so any A2A-aware dispatcher can orchestrate Task-Specs:

11 Backlog architecture — five layers of state

Every state change is atomic + logged + git-committed; crashes are recoverable by design. Frontmatter is authoritative; everything derived can be rebuilt.

Layer 1 · git

The permanent record. Every transition is a commit; history is the audit trail of last resort.

Layer 2 · tasks/ folder

The backlog itself: active specs at the root, done/ and parked/ subdirs via archive.sh, optional queue/ for batch output.

Layer 3 · frontmatter status

The authoritative per-file truth. Changed only through transition-status.sh (lock + ledger) — hand-editing bypasses both.

Layer 4 · _state.yaml

Derived index for fast queries. Rebuildable at any time with rebuild-state.sh; a pre-commit hook catches drift from direct writes.

Layer 5 · _metrics.jsonl

Append-only forensic ledger — one JSON line per event, queried by query-metrics.sh. Never rewritten, only appended.

The invariant

Successful validation idempotently snapshots frontmatter into _state.yaml; failed validation writes nothing — broken specs never pollute the audit trail.

“Specs that verify themselves keep humans at the edges of the loop — at intent-setting and acceptance review — not in the middle of every iteration.” That's the whole thesis: the mission is to be the open, atomic, vendor-neutral, self-verifying unit-of-work format any conformant agentic system can produce, consume, and trust.
