03 Pass 1 · brd-docs-to-tech-req — the client hands you the problem; you produce the spec

Reads a client BRD like a senior engineer, not a stenographer: finds the real problem underneath the ask, grills the 2–3 questions whose answers most change the build, and crystallizes one tech-spec with falsifiable requirements and metrics traced to the BRD's KPIs. Ambiguity killed here is the cheapest kill in the whole descent.

Flow
Understand → Interrogate → Crystallize

Read the BRD → grill the questions that most change the build → resolve into one technical answer.

Ships
check-tech-spec.sh
--engine cowork · --out-format pdf

The gate linter: scope, data, and success metric named; every requirement falsifiable.

Gate
The spec answers the brief

You can restate the client's problem in one breath and show the tech-spec answers it.

04 Pass 2 · tech-req-to-adrs — greenfield or brownfield, and write the ADRs

Names the ground (brownfield = a system you didn't write), opens the system end to end, reconciles the spec against real schemas, sources, and jobs, and records each grounding decision as a numbered ADR under docs/adrs/. An ADR records what is true — never how to build. The moment an ADR says "build X", you've drifted into planning.

Flow
Name the ground → Check → Record

Brownfield vs greenfield, explicit → reconcile spec vs reality → durable ADRs Pass 3 can stand on.

Ships
scaffold-adr.sh
engine fixed: Claude Code on the repo

Numbered ADR scaffolds — facts and constraints, terrain altitude only.

Gate
Terrain understood, recorded durably

Pass 3 can read the decisions without re-deriving the terrain.

05 Pass 3 · reqs-to-swimlane-plans — split the work along its natural seams

ADRs in hand, this pass cuts where the system is already jointed and gives each seam one sketch/swimlane-<seam>/ directory: a lean PRD plus one file per leg. The leg key is stable and technology-less; the filename may carry the current tool label. Plan altitude stays above tasks and implementation code.

Flow
Seam → Swimlane → Leg → Task-Spec

Cut on real joints → one lane directory per seam → independently finishable legs → Task-Spec leaves at Pass 5.

Ships
new-plan.sh
v0.7.0 · dir-per-swimlane · CHECK_PLAN

Cross-file scaffolds and checks for PRDs, leg metadata, links, contiguous ids, architecture, and seam contracts.

Gate
One plan per genuine seam

Plan-altitude held; the downstream lane names the exact upstream interface it consumes.

06 Pass 4 · sketch-plans-adversarial-review — a different model refutes the plans

A model will not refute itself hard enough, so this pass dispatches a different-family engine (cvg review --adversary codex|kimi|claude) as a skeptic. Every objection is FIXED in a plan or ACCEPTED with a named owner. The referee—not the engine—stamps live-plan SHA-256 provenance into one objection log, and cvg review --check re-hashes it before handoff.

Flow
Attack → Ground → Sharpen

Refute one plan at a time → check vs tech-spec + ADRs for contradictions, gaps, silent assumptions → fix or own.

Ships
check-consensus-gate.sh
attack-playbook.md · engine-adapter.md · schema

Single- and multi-engine dispatch, fail-closed timeout/error states, provenance stamping, and the consensus gate.

Gate
No objection survives · provenance intact

The proving ground closed with eight resolved objections over all twelve plan files and CHECK_CONSENSUS=OK.

The current decision: the fork is collapsed. Task-Spec v3.4 treats oversized work as XL/XXL decomposition nodes with required children; workers receive only runnable leaves. The plan-driven branch is retained as repository history, not an active handoff.

08 Pass 5 · task-spec — the single tasking path · v3.4.0

The deepest skill in the chain: atomic, vendor-neutral, self-verifying Task-Spec v3 units. Each tasks/T-*.md carries frontmatter + six zones + ≥3 runnable bash evals + an Exit Check — the definition of done travels inside the file. This is Eval-Driven Development: humans at intent and acceptance, never in the middle.

The two gates are duals

PRE — safe-to-delegate.sh --stamp certifies the spec: evals well-formed, assertion failure expected, HMAC-seals the eval bodies. POST — accept-task.sh --stamp certifies the work: clean-checkout eval pass, blast radius, HMAC recheck, optional gold-sanity Goodhart guard.

The runtime

Locked atomic status transitions, rebuildable _state.yaml index, append-only _metrics.jsonl ledger, six-tier sizing (XS/S/M/L leaves; XL/XXL nodes), leaf-only delegation, L0–L2 executor conformance, and an open execution-backend contract.

Ships

20 scripts · 31 reference files · 19 runbooks · JSON Schemas (Draft 2020-12) · test + conformance suites. Deep dive: the full anatomy page · content updated to v3.4 inside the legacy-stable filename.

Gate: every task carries a runnable eval — no eval, not a task yet. The sign-off envelope is HMAC-SHA256; hand-stamping is rejected. A task is provably DONE only when accept-task.sh writes accepted: true.
09 ① Register · task-specs-to-issues — the tracker as state

Projects each signed-off Task-Spec onto exactly one tracker issue (--tracker github|linear|jira), with blocked-by links carrying the depends_on graph — so the loop reads a board instead of re-deriving state. The tracker is a pluggable backend behind a two-method adapter: read ready / write result.

Mechanic
1 spec = 1 issue, no drift

1:1 projection; dependency edges become blocked-by links; the build order lives in the tracker itself.

Ships
register.sh · verify-registration.sh
--tracker github|linear|jira

Registration + the integrity check: no orphans, no cycles (DAG ⇒ dispatch terminates).

Gate
The board never lies

count(issues) == count(signed-off specs). Only the loop writes state; only a green eval closes an issue.

10 Pass 6 · stack-to-harness — the quality moat (+ the engine it drives)

Reads which techs the in-scope tasks put in play and scaffolds the control plane fitted to exactly that stack — never speculatively. Thin orchestration over agents-kbs-tech-stack, the bundled engine. The stack fills the harness; the tasks point at it.

Paired architect (no Bash) + developer (has Bash) per tech, full KB trees, three universal closers via the closer-hook protocol, tunable doctrine.yaml.

Cross-tool mirrors
One contract, every engine

Why it's a moat: the control-plane files that make any commodity agent succeed are not downloadable — they're built, tested, failed, and rebuilt. Gate: the control plane stands and is grounded; quality-gate.sh is green; mirrors emitted.
11 Pass 8 · task-loop — one issue → green-eval PR

The execution loop you build (the Manager that schedules it is a future CI/CD concern). Takes ONE issue (--issue N), reads its task-spec + cited ADRs + grounded harness, cuts a branch, writes code, runs the task's own eval. RED: feed the failure back and revise — a tight local loop.
