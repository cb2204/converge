Task-Spec

Release v0.1.0 · format_version 3 · hmac-sha256-v2

A Task-Spec is the smallest unit of work that can be delegated, verified, accepted, and audited without guessing. It binds intent to executable evidence, then hands runtime authority to Converge without letting either the worker or the tracker redefine “done.”

01

The contract’s role

Task-Spec occupies the seam between planning and execution. It is detailed enough for a conforming executor, but remains independent of any single model, IDE, tracker, or orchestration vendor.

It is
  • A signed unit of delegated intent
  • A dependency node
  • A behavior-to-evidence map
  • A lifecycle record
  • A portable execution contract
It is not
  • A generic ticket
  • A chat prompt
  • A mutable dashboard row
  • A runtime permission grant
  • A substitute for architecture
It enables
  • Deterministic delegation gates
  • Parallel frontier resolution
  • Independent acceptance
  • Trust-aware automation
  • Auditable retries and handoffs
Release versus data format. The packaged method is Task-Spec v0.1.0. Documents use format_version: 3. The first identifies the release; the second selects the schema family inside the file.
QuestionOwned byEncoded asMay not be overridden by
Why does the work exist?Accepted planning and task authorIntent, scope, non-goals and behaviorWorker preference or tracker summary
What counts as done?Task contractCriteria, eval mapping, validation card, exit checkImplementation narrative
What may execution touch?Authorized task + Pass 7 bindingSealed paths, capabilities and repo gateConvenient tool arguments
Which work is ready?Canonical DAG and lifecycleDependency-ready frontier; PRE eligibility is checked separatelyTracker order or agent enthusiasm
Was the work accepted?Independent refereePOST stamp, evidence and accepted: trueWorker self-report

This separation is why a Task-Spec is more than a detailed ticket. A ticket can describe work while leaving authority and verification implicit. A Task-Spec must remain sufficient when the author, worker, verifier, and dashboard are four different systems with no shared private context.

02

The six-zone anatomy

The body is read top-to-bottom as a proof argument: why, what, how success is measured, what action is forbidden, which unknowns remain, and how to recover.

1

Intent

Goal and lean context: why the task exists, what outcome matters, and which accepted source carries the broader rationale.

2

Behavior

Atomic observable requirements, each addressable by identifier and linked to evidence on standard and full profiles.

3

Contract

Runnable success criteria, validation card, exit check, and the exact boundary between claim and acceptance.

4

Guardrails

Specific anti-patterns and do-not-touch paths that bound the worker’s behavior and blast radius.

5

Operations

Open questions and honest unknowns. Anything unresolved enough to prevent safe work becomes a first-class blocker, not a hidden assumption.

6

Rollback + observability

Recovery procedure, expected duration, failure signals, metrics, and alerts required by the full profile.

ZoneCompleteness testRed flagDownstream consumer
IntentA reviewer can explain outcome and non-goals without guessingRestates a solution but never names the problemWorker reasoning and holdout rubric
BehaviorEvery item is observable and has a stable identifier“Improve,” “support,” or “handle” without a conditionEval traceability and change review
ContractA fresh verifier can reproduce pass/failSuccess depends on the author’s interpretationPRE, POST and Tier 2
GuardrailsAuthorized and prohibited effects are explicit“Touch files as needed” or broad repository scopeBinder, repo gate and blast-radius check
OperationsEvery open question is answered or represented as a concrete blockerAn unresolved unknown is buried in prose while status remains readyHuman escalation, readiness and recovery
Rollback + observabilityA failed rollout can be detected and safely reversedRollback says only “revert” with no state or signalFull-profile acceptance and operations

This is a copy-safe pre-PRE frontmatter shape using the live field names. Plain cvg tasks gate <spec> does not write Task-Spec or Converge metadata, but still executes declared eval code. cvg tasks gate --stamp <spec> is mutating: on a re-seal it removes the superseded signature before validation, then writes signed_off: true, signed_off_by, signed_off_at, and—when a key is available—a fresh v2 signature only after success. A failed re-seal may leave the spec structurally signed but cryptographically unsealed; repair it and re-stamp successfully. Identity makes the file addressable; topology controls readiness; scope constrains effects; effort and backend control eligibility; budgets constrain autonomy; acceptance remains false until POST.

04

Profiles: proportional rigor

Profiles change required evidence, not the definition of correctness. The default is standard; the lightest profile is named lite, not “minimal.”

ProfileBest fitRequired shapeDo not use when
liteSmall, low-risk, local, obvious changesGoal + runnable Success Criteria + Validation Card + Exit Check; Behavior and surrounding zones may be omittedAnother engineer needs full rationale, guarded scope, or traceability
standard · defaultNormal production engineeringLite core + Behavior, Context, Anti-Patterns, Do-Not-Touch, Open Questions, and bidirectional behavior/eval traceabilityRollback and observability need first-class detail
fullUnattended, security/financial-critical, or hard-to-reverse workStandard + explicit Rollback Plan and Observability HooksThe added recovery and runtime evidence would be ceremonial rather than informative
Choose by consequence, not page count. A tiny authentication change may deserve full; a large generated fixture update may remain lite if risk and ambiguity are genuinely low.
Escalate for uncertainty

Choose a stronger profile when requirements, interfaces, data migration, operating environment, or acceptance evidence are not obvious—even if the code diff is expected to be small.

Escalate for consequence

Security, privacy, money, availability, irreversible state, external writes, broad blast radius, and difficult rollback justify deeper guardrails and observability.

Do not de-escalate by confidence

An agent or author feeling confident is not evidence. Lower rigor only when the objective risk, coupling, and recovery surface are genuinely smaller and policy permits it.

05

Behavior and bidirectional traceability

For standard and full, every behavior must be evidenced by one or more evals, and every eval must justify itself by tracing back to behavior.

Good behavior

Observable, atomic, unambiguous, and stated independently of a preferred implementation.

Bad behavior

“Improve export reliability.” It has no observable condition, failure boundary, or evidence mapping.

Behavior qualityWeak wordingContract-grade wording
Positive path“Export works”Given an authorized dataset, the command exits 0 and writes JSON conforming to schema v1
Negative path“Handle bad paths”A destination outside the allowed root exits 2, names the violation, and creates no partial file
Idempotency“Safe to retry”Repeating the same request key returns the original result and creates no second export
Compatibility“Do not break old clients”Existing v1 fixtures produce byte-equivalent required fields and retain documented exit codes
Observability“Add logs”Each attempt emits task ID, outcome, duration and record count without secrets or payload content
06

Validation cards and runnable evals

The validation card turns acceptance from a paragraph into a reproducible protocol. Evals should be independently runnable, deterministic where possible, and explicit about fixtures and expected results.

Arrange

Environment, fixture, prerequisites, seed, and clean-state assumptions.

Act

Exact command or procedure, including working directory and required configuration.

Assert

Exit code, output, state transition, invariants, and prohibited side effects.

success_criteria: - id: eval_3 description: Reject outside-root destination runnable: bash check_type: deterministic verifies: [B-2, B-3] terminal: true expected_duration_sec: 5 # The live card also carries retry_policy and agent_contract. # A separate “## Exit Check” fenced bash block composes: eval_1 && eval_2 && eval_3
An eval is not “run the test suite.” Broad suites can be part of acceptance, but each critical behavior still needs a legible proof path and an expected failure surface.
Current enforcement split. Validation/PRE hard-fails a behavior with no proving eval and a dangling behavior ID, but an eval missing verifies: is only a warning there. cvg tasks dod hard-fails that reverse-link gap and is the current full bidirectional traceability gate.
Determinism checklist

Pin fixtures, clocks, seeds and working directory where practical. Declare required services and environment variables without embedding secrets. Make cleanup explicit. A rerun on the same revision should produce the same verdict or explain the controlled source of variation.

Independence checklist

POST must be able to invoke the eval without the worker’s conversation, unstated local setup, or hand-edited result. The command should inspect actual state and return a meaningful non-zero code when the predicate fails.

Use cvg tasks dod <spec> to inspect the definition-of-done and traceability matrix, then cvg eval <spec> to execute the declared evals. The first checks the shape of the proof argument; the second produces runtime evidence. Passing one cannot substitute for passing the other.

Six effort tiers and the runnable-leaf rule

Sizing is an execution policy. XS through L are runnable leaves. XL and XXL represent decomposition nodes and must become smaller tasks before delegation.

TierExecution ruleTypical shapePrimary question
XSRunnable leafSingle obvious edit and focused checkCan it be verified in one narrow step?
SRunnable leafSmall coherent changeAre scope and dependencies trivial?
MRunnable leafNormal multi-file engineering taskCan one worker own the whole contract?
LRunnable leaf on configured long-horizon backendExtended but coherent executionAre checkpoints, budgets, and recovery sufficient?
XLMust decomposeMultiple independently acceptable outcomesWhere are the child boundaries?
XXLMust decomposeProgram or initiative nodeWhat DAG makes progress independently verifiable?
L is not GLM-only. The current policy accepts configured long-horizon backends; defaults include GLM, Claude, Codex, and Kimi where installed and authorized.
Write-surface counts are warning-only sizing guidance today. The validator compares XS/S/M/L against 1/2/3/5 declared write paths and warns when a leaf exceeds its tier; PRE may still pass. By contrast, the configured long-horizon backend requirement for an L leaf is a hard error.
08

Dependencies and the ready frontier

Tasks form a directed acyclic graph. cvg ready computes only the dependency-ready set: files whose own status is ready and whose dependencies are done, with legacy accepted tolerated for compatibility. PRE eligibility remains a separate gate before delegation.

Dependency means

A predecessor produces an artifact, invariant, schema, interface, or decision required for this task’s success—not merely that someone prefers an order.

Parallel means

Tasks can execute concurrently only when their path scopes, mutable resources, acceptance evidence, and integration points do not create hidden coupling.

Cycles are specification defects. A cycle usually means responsibilities are entangled or an integration task is missing. Do not teach a queue to guess around it.
Queue operationPredicateMutationFailure behavior
cvg readyStatus is ready and every dependency is done (legacy accepted also tolerated)NoneOmit blocked nodes and print the hidden count; --all lists them
cvg ready --allStatus is ready regardless of dependency resolutionNoneList the ready-status files; no per-task blocker explanation
cvg lintDAG is acyclic and path scopes do not overlap unsafelyNoneNon-zero with concrete cycle or overlap
cvg transition <id> <state>Target status is valid; an actual state change to done also requires acceptance provenance and a matching pass receiptCanonical frontmatter plus ledger eventSame-state requests return immediate NOOP before the done guard; other changes reject failed invariants without partial update, but no source-state edge matrix is enforced

A dependency should describe a produced prerequisite, not a vague preference for order. If two tasks merely edit the same file, that is a scope-overlap problem; it may require decomposition or sequencing, but does not automatically mean one semantically depends on the other. Clear topology lets the queue expose safe parallelism without pretending shared mutable state is independent.

09

The lifecycle state machine

Status records operational reality. For an actual transition into done, acceptance must be stamped and a matching passing execution receipt must exist; a worker claim is insufficient.

StatusMeaningRequired evidence
readyEligible once dependencies, PRE, and executor policy holdValid current contract
in-progressClaimed by an active execution ownerClaim/lease identity
blockedCannot advance under current authorityConcrete blocker + required resolver
donePOST-accepted work with passing execution evidenceaccepted: true, accepted_by/accepted_at that are nonempty and not literal (none), and parseable cvg/receipts/<id>.json whose exact task_id matches and exact result is pass
parkedIntentionally outside the active frontierReason and re-entry condition
Blocked is actionable

A blocker names the missing dependency, authority, environment, decision, or external state and identifies who or what can resolve it. “Agent could not finish” is not a useful blocker because it gives the queue no re-entry condition.

Parked is intentional

Parking removes work from the active frontier without declaring failure. Record why priority changed, what evidence remains valid, what may go stale, and which explicit event or decision can return it to ready.

Lifecycle is not loop state. Task status records backlog reality; TASK_LOOP=STALLED records one controller outcome. A stalled attempt may transition a task to blocked, but the two taxonomies should not be merged or copied blindly. The shipped transition tool enforces evidence only on an actual change into done: it checks the exact fields above, but does not authenticate receipt provenance or validate hashes, profile, full receipt schema, or a source-state edge matrix. The ready, in-progress, blocked, and parked evidence in this table is normative method guidance rather than an enforced transition-edge policy. A request to transition an already-done file to done returns NOOP before re-running the done evidence checks.
10

PRE: safe to delegate

cvg tasks gate <spec> invokes the safe-to-delegate checks and returns a verdict without writing Task-Spec or Converge metadata, while still executing declared eval code. Only cvg tasks gate --stamp <spec> may mutate the envelope: on a re-seal it retires the superseded signature before validation, then writes a fresh PRE envelope only after the gate passes. Neither form predicts implementation success; both prevent obviously invalid delegation.

Parse and validate structure.

Check format version, required fields, profile rules, identifiers, and normalized values.

Validate behavior and evidence.

Hard-fail uncovered behavior and invalid references; warn when an eval lacks verifies:; use cvg tasks dod for the full reverse-mapping gate.

Validate topology and size.

Reject missing dependency references, non-runnable XL/XXL nodes at PRE, and unsupported backend combinations. Whole-backlog cvg lint detects cycles.

Validate authorization.

Check allowed paths, execution policy, budgets, agent, and keyed HMAC integrity.

Stamp only when explicitly authorized.

After a passing verdict, cvg tasks gate --stamp binds the validated body and authority fields to the PRE envelope.

11

HMAC v3: tamper evidence for delegation

A keyed digest proves that the canonical body and execution-relevant authorization fields have not changed since an authorized signer stamped them.

Covered
  • Extracted body text, syntax-sensitive
  • touches_paths and creates_paths
  • depends_on, requires, and effort
  • execution_backend and agent
  • budget_iterations and optional budget_tokens
  • The PRE sign-off envelope itself
Not promised by HMAC
  • That the task is a good product decision
  • That the implementation will succeed
  • That a key was handled safely
  • That external state remains unchanged
  • That the signer was authorized by organizational policy
  • That POST acceptance has passed
Tamper evidence, not encryption. HMAC does not hide task content. It detects unauthorized mutation when the verification key remains controlled.
Serialize exactly.

The reference code hashes the extracted body text and serializes authorization fields in a fixed field-name order, preserving each field block except trailing whitespace.

Sign.

Compute HMAC-SHA256 with the repository-local key kept outside version control; record algorithm, key identity where appropriate, and digest.

Verify before binding.

Recompute from the current file. A mismatch means authority changed or the key context is wrong; both require a hard stop.

Re-authorize changes.

Review the material diff, rerun validation, and create a new stamp. Never copy the old digest or exclude a convenient field to make it pass.

The seal is syntax-sensitive, not semantic YAML normalization. Reformatting body text, indentation, or equivalent inline-versus-block list syntax can change the digest. Signers and verifiers must use the same reference functions and fixtures before claiming Tier 1 compatibility.

13

Execution: the contract stays canonical

The worker receives the task identity and a Pass 7 runtime contract. It is not authorized to expand scope or redefine acceptance. Current portable postflight policy can detect Git-visible repository changes outside declared scope at settlement. Ignored or out-of-repository effects require installed runtime, pre-tool, or OS controls; only preventive controls can stop mutation before it occurs.

Worker owns

Implementation strategy, local investigation, allowed edits, and repair within the contract.

Harness owns

Tools, permissions, secrets, context, working directory, timeout, and process lifecycle.

Referee owns

PRE validity, independent evals, POST acceptance, blast radius, integrity, and terminal state.

Runtime binding is separate. Task-Spec says what successful work means. The derived runtime contract says which capabilities and resources may be used to attempt it.
14

POST: accept the work

cvg tasks accept <spec> invokes the acceptance gate and reports whether implementation evidence satisfies the original contract without writing Task-Spec or Converge metadata; it still executes declared eval code. Only cvg tasks accept --stamp <spec> writes the acceptance envelope after that verdict passes.

Resolve the available integrity tier.

POST attempts keyed HMAC verification when the key, signature, and crypto provider are available. Missing material can yield a structural-only Tier 2 note and does not by itself block acceptance; unattended Tier 1 policy must be enforced separately.

Run validation and exit checks.

Execute the declared evidence protocol rather than trusting worker-reported results.

Inspect blast radius when available.

By default, compare Git change data with authorized scope. --no-blast-radius or a non-Git environment leaves scope unchecked and may still accept, so strict policy must prohibit that weaker path.

Apply optional gold sanity.

Run protected reference cases or high-value invariants where the profile and policy require them.

Stamp acceptance explicitly.

After the metadata-nonwriting verdict passes, cvg tasks accept --stamp writes accepted: true, accepted_by, accepted_at, and an acceptance metric. It does not change status; done still requires the matching passing execution receipt and an explicit transition.

Acceptance is not automatically Tier 1. A green POST verdict can be structurally valid when keyed verification is unavailable. If policy requires cryptographic authorization, require and verify Tier 1 outside the acceptance script before treating the stamp as sufficient.
15

The five-layer backlog state model

Task state is durable, reviewable, and rebuildable. No single database or UI is allowed to become an opaque authority.

1 · Git

Immutable history, review boundary, authorship, and versioned change record.

2 · Files

Human-readable, tool-portable Task-Spec documents.

3 · Frontmatter

Canonical current lifecycle, identity, topology, scope, execution, and trust fields.

4 · Index

Rebuildable query and queue projection derived from canonical files.

5 · Ledger

Append-only created, accepted, and status_change events today. Loop attempts and checkpoints live separately under cvg/loop/.

Projection test. If deleting and rebuilding the index changes task truth, the architecture has inverted its authority.
ConflictAuthorityRecovery
Tracker says done; Task-Spec says in-progressTask-Spec acceptance envelope plus matching execution receiptCorrect projection; do not synthesize acceptance
Index says ready; dependency file is not doneCanonical dependency frontmatterRebuild index and record drift diagnostic
Ledger lacks an event but file contains a valid transitionCurrent file for state; git for historyReconcile with an explicit repair event, never rewrite old ledger
File digest and PRE stamp disagreeIntegrity gateBlock, review material change and re-stamp
Two files claim the same task IDUniqueness invariantBlock queue and registration until identity is resolved

Rebuildability is an operational feature, not only an architectural preference. It lets a corrupted cache, failed migration, or replaced dashboard recover from reviewed source without inventing task state. The append-only ledger complements this by showing how the current state was reached and which external projections may need reconciliation.

Executor conformance levels

Portability is graduated, but the current conformance suite is a narrow legacy lifecycle-and-retry harness. An implementation should publish exactly what its claimed level was observed to do.

LevelCurrent harness scenarioObservable assertionNot certified by this level
L0 · EvalDrive a signed solvable fixtureThe fixture’s Exit Check passes after executionLifecycle, lock, scope, trust, or receipt semantics
L1 · LifecycleL0 plus the ready → in-progress → done expectationThe current harness observes final status: done; it does not observe intermediate lock acquisitionPRE/POST, HMAC, receipts, Bind, or guarded done
L2 · RetryL1 plus an unsatisfiable fixture bounded by budget_iterationsThe executor returns before the harness timeout with final status: parkedReason content, complete current lifecycle, runtime authority, or Loop terminal truth
Conformance evidence

Publish parser fixtures, valid and invalid examples, lifecycle tests, traceability cases, signature vectors, scope escapes, and exact exit semantics—not only a logo or README claim.

Graceful degradation

An executor must refuse contract features it cannot enforce. It must not silently ignore full-profile rollback, keyed integrity, runtime binding, or a guarded lifecycle requirement merely because the legacy fixture is green.

Current clause coverage

The wider Task-Spec test suites exercise additional clauses and end-to-end flows separately. They do not turn one executor’s CONFORMANCE=L2 token into full current-protocol certification.

Current fixture gap. The bundled ref-executor.sh writes done/parked frontmatter directly. It does not exercise the portable state lock, PRE/POST, HMAC, pass receipts, Bind, Loop terminal truth, or the guarded transition-status path. Its self-test is useful, but it is not proof of complete 0.1.0 L1/L2 lifecycle enforcement.

A disciplined authoring workflow

Start from accepted planning.

Use Pass 4-hardened swimlanes and preserve their intent, dependencies, architecture, and objections.

Choose profile and effort honestly.

Use consequence and executor policy; decompose XL/XXL nodes before delegation.

Write behavior before evals.

Define observable outcomes, then map each one to independently runnable evidence on standard and full profiles.

Define scope and failure behavior.

List authorized paths, prohibited changes, non-goals, open questions, and profile-required recovery evidence.

Set topology and Task-Spec resources.

Resolve depends_on, backend compatibility, agent policy, budget_iterations, optional budget_tokens, and Validation Card agent_contract.timeout_minutes. Loop reads those task values for its configured brakes; Bind hash-binds the Task-Spec and points to its budget fields without copying them.

Validate, seal, review.

Run structural validation, PRE stamping, and human review before unattended execution.

$ cvg tasks validate cvg/tasks/T-20260729-export-format.md # structure + sizing $ cvg tasks gate cvg/tasks/T-20260729-export-format.md # metadata-nonwriting PRE verdict; evals still run $ cvg tasks gate --stamp cvg/tasks/T-20260729-export-format.md # write PRE envelope $ cvg bind --task cvg/tasks/T-20260729-export-format.md # Pass 7 binding $ cvg loop --issue T-20260729-export-format --estimate # configured controls; not a spend forecast; setup runs first $ cvg loop --issue T-20260729-export-format --resume # restore state.env counters; no stale-state validation $ cvg loop --issue T-20260729-export-format --gate-only --dry-run # controls preview; exits DRY_RUN=OK before eval/settlement $ cvg loop --issue T-20260729-export-format --agent codex # settles + attempts pass-receipt write; confirm it # Standalone proof roles: eval = Tier 1, verify = Tier 2; neither settles or transitions: $ cvg eval cvg/tasks/T-20260729-export-format.md $ cvg verify --task cvg/tasks/T-20260729-export-format.md --judge claude # Separate Task-Spec POST and lifecycle operations: $ cvg tasks accept cvg/tasks/T-20260729-export-format.md # metadata-nonwriting POST verdict; evals still run $ cvg tasks accept --stamp cvg/tasks/T-20260729-export-format.md # write acceptance # done checks accepted=true, by/at nonempty and not (none), parseable receipt, exact task_id/result=pass: $ cvg transition T-20260729-export-format done

All Loop entry modes require --issue. Without global --dry-run, --gate-only may still write a receipt and perform configured branch, commit, push, or PR settlement. With --dry-run, Loop performs initial setup, prints resolved controls, then exits DRY_RUN=OK before worker, eval, settlement, receipt, push, or PR; it emits no TASK_LOOP verdict. Initial worktree setup/cleanup can still occur. Resume shell-sources state.env without stale-state validation; default worktree isolation can restart at attempt 1. Same-state done returns NOOP before the evidence guard.
