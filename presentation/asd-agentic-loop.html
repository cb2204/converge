01

Three levels, three different questions

The words “agent,” “loop,” and “autonomy” are often collapsed into one vague idea. Keeping the levels separate makes the architecture testable.

Runtime anatomy

The Agentic Loop

Explains how one model invocation becomes tool calls, environment changes, and a deterministic judgment.

Delivery method

Converge

Explains how product intent descends through Passes 0–8 into accepted work and durable receipts.

Engineering discipline

ASD

Explains how to design, build, verify, operate, and evolve the autonomous system itself.

System, not chatbot. A useful autonomous system includes the model, harness, tools, environment, referee, contracts, budgets, recovery paths, and evidence trail. The conversational surface is only one component.
If this question is being asked…Look at this levelCorrect evidenceTypical category error
Why did the model request this command?Agentic LoopPrompt context, tool schema, model request, observationBlaming “the agent” without identifying harness policy
Why did this task exist and what must it prove?ConvergePass artifacts, Task-Spec, and gate evidenceTreating runtime logs as product authority
Why was this system allowed to operate unattended?ASDThreat model, capability envelope, budgets, recovery and assurance caseUsing model benchmarks as a safety case

The levels are compositional. ASD produces a safe system; that system implements Converge; Converge drives many individual agentic loops. A failure can propagate upward, but diagnoses should begin at the lowest boundary that can explain it. A malformed tool argument is a runtime defect. A task with no meaningful success criterion is a method defect. A system that lets either defect mutate production without a referee is an ASD defect.

02

The five-layer runtime

Layers 1–4 make work possible. Layer 5 makes the result trustworthy. Boundaries are explicit so a persuasive model response cannot masquerade as proof.

LayerOwnsMust not claimEvidence
ModelInterpretation, plans, candidate editsThat commands ran or criteria passedText and structured tool requests
HarnessConversation, permissions, fresh processesThat outcome quality is acceptableInvocation logs and exit codes
ToolsSpecific actions exposed by schemasAuthority beyond their capabilityTool results
EnvironmentMutable state: files, git, databasesIntent or policyDiffs, records, state snapshots
RefereeIndependent checks and settlementCreative implementation choicesGates, verdicts, receipts, and reruns
Control path

Authority moves from human policy to orchestrator, harness, tool, and environment. Every hop should narrow capability or preserve it; no lower layer may manufacture new authority. A task that authorizes edits under src/export/ cannot be widened by a prompt, tool parameter, or convenient shell glob.

Evidence path

Observations move in the opposite direction: environment state becomes tool output, the harness records it, and the referee interprets it under the contract. The orchestrator emits terminal state and attempts the settlement receipt. The complete evidence set—not the current receipt alone—must correlate task identity, versions, commands, exit codes, logs, verdicts, and relevant hashes.

Layer-collapse warning. If the model both chooses the test, reports that it passed, and changes the acceptance state, there is no independent referee. If the harness can silently broaden paths because a command failed, there is no capability boundary. Architecture diagrams matter only when those separations survive failure.
03

One agentic turn, step by step

A turn is not “AI edits code.” It is a protocol. Every boundary has an input, output, and failure mode.

Load authority.

The orchestrator supplies an identifier-bound runtime contract, not a prose blob that silently expands scope.

Expose capabilities.

The harness describes tools, permissions, budgets, and the working environment to the model.

Act through tools.

The model requests actions; the harness authorizes and executes them. The model never owns the shell directly.

Judge outside the narration.

The referee reruns gates and maps machine evidence to a terminal state. A confident final message is not a verdict.

A tool error is returned to the model as data, not quietly retried by an invisible subsystem. This lets the worker change strategy while keeping the orchestrator’s attempt budget honest. Control-plane failures normally become ERROR; explicitly best-effort sinks such as tracker narration and the current receipt writer are reported separately and do not change the task verdict, so downstream closure must confirm their evidence.

04

How the model knows what exists

Models do not wake up knowing the repository, CLI, or policy. The harness assembles a finite context package; discovery remains an explicit action.

Prompt context
  • Task identifier and immutable authority
  • Relevant repository instructions
  • Tool names, parameter schemas, and permissions
  • Prior observations within this attempt
  • Budget and stop conditions
Environment discovery
  • Read-only inspection before mutation
  • cvg agent-context for machine-facing surface and syntax
  • Source and tests for semantic boundaries
  • Repository search for canonical sources
  • Version and gate checks before assumptions
  • Fresh observations on every retry
Context is not memory and memory is not authority. Cached summaries can guide search; current files, executable behavior, gates, and service state establish truth.
Context assembly rule

Start with immutable identifiers and compact policy, then add only the files and observations needed for the present decision. Include provenance—path, revision, timestamp, or service identity—so the model can distinguish a current source from an old example. When two sources disagree, surface the conflict instead of averaging them.

Context retirement rule

Do not carry speculative reasoning, obsolete errors, or superseded source text into every retry. Persist only durable facts and explicit evidence artifacts. A fresh worker should learn that attempt 1 failed a path-fence check, not inherit the entire monologue that led attempt 1 there. This keeps failures local and makes progress fingerprints meaningful.

05

Converge sits in two seats

The same CLI can be available inside the agent’s tool surface and outside it as an independent referee. The authority boundary—not the binary name—is what matters.

Inside · environment tool

Help the worker navigate

The agent may inspect the task, run permitted setup commands, and invoke local validators. These observations inform implementation but do not settle it.

Outside · referee

Judge after the worker stops

The orchestrator invokes independent gates, verifies seals and receipts, and determines whether the attempt settles, retries, or hands off.

$ cvg agent-context # worker-facing discovery $ cvg bind --task cvg/tasks/T-20260729-export-format.md # derive runtime authority $ cvg loop --issue T-20260729-export-format --agent codex # bounded fresh-process loop $ cvg eval cvg/tasks/T-20260729-export-format.md # run declared evidence $ cvg verify --task cvg/tasks/T-20260729-export-format.md --judge claude # Tier 2 holdout

Inside the worker, cvg eval <spec> can provide fast feedback, but the result is advisory until the outer referee reruns it from a known state. Outside the worker, cvg bind --check --task <spec> rechecks the bound contract, POST evaluates acceptance, and Tier 2 grades the actual diff. Direct cvg verify reads stated intent but does not independently validate PRE/HMAC, so upstream integrity must already be established. The same binary may occupy both seats, but the worker must not control the invocation, inputs, or interpretation that settles its own work. Standalone eval is Tier 1 evidence, verify is Tier 2, and tasks accept is POST; none attempts, retries, settles, or changes lifecycle status. Full Loop coordinates runtime work but does not stamp POST or transition the task to done.

Why this is not duplicated work. Inner checks accelerate repair; outer checks establish trust. Compiler diagnostics inside an editor do not replace CI, and worker-run evals do not replace referee-run acceptance. The two runs answer different questions under different authority.
06

The Pass 8 loop kernel

The task-loop skill and cvg loop --issue <id> command form the control kernel: obtain authority, launch a fresh worker, verify independently, classify the evidence, and either settle or start another bounded attempt. Normal, --estimate, --resume, and --gate-only modes all require --issue. Gate-only is a single-shot eval/path-policy settlement path, not inherently read-only. With global --dry-run, Loop performs initial setup, prints resolved run controls, then exits DRY_RUN=OK before worker, eval, settlement, receipt, push, or PR work; it emits no TASK_LOOP verdict.

Fresh process per attempt. The next worker receives the contract, durable workspace evidence, and the prior failure log—not an ever-growing private conversation. This limits context drift and makes retries inspectable.

The shipped Loop distinguishes evidence refusal from retry and control failure. BLOCKED means a candidate cannot settle under current evidence or policy—gate-only RED, Tier 2 refusal/unusable verdict, or settlement refusal. STALLED is repeated ineffective repair, EXHAUSTED is a pre-attempt limit, and invalid task/contract resolution is ERROR. Dependency readiness belongs to the dispatcher/method prerequisite; Loop does not inspect it.

07

Bounded autonomy: budgets and stagnation

“Keep trying” is not a control policy. Before another worker attempt, the loop checks an iteration cap and accumulated working time; an optional token brake checks only worker usage the adapter reports. It does not interrupt an in-flight attempt or recheck those counters before Tier 2, so time and token are pre-attempt brakes rather than strict end-to-end ceilings. Stagnation detection stops retries that no longer produce new information.

Progress fingerprint

The current kernel normalizes the [pass]/[fail] and Exit Check lines, removes timing noise, and hashes that signal. A new failure can be progress; the same signature repeated is not.

Stagnation detector

When successive attempts reproduce the same normalized check evidence, stop with STALLED and preserve the attempt log, checkpoint state, and handoff for a human.

Budgets are safety properties—with a precise enforcement boundary. Iteration, elapsed-work, and configured reported-token counters are checked at the top of the worker-attempt loop. An attempt may cross a time or token threshold before control returns; Tier 2 usage and unreported provider usage are not metered by those checks.

08

Settlement and the Tier 2 holdout

Completion is a claim; settlement is a verified state. In shipped Pass 8, the sealed eval runs first, an optional Tier 2 verifier challenges the green candidate, and settlement attempts to write the passing execution receipt. Task-Spec POST remains a separate referee step afterward. The current settler does not fail its success token when receipt writing fails, so operators must confirm the receipt before lifecycle closure.

Worker claims completion.

The harness records its candidate result but does not treat it as final.

The sealed eval runs.

The Task-Spec’s runnable proof and settlement path checks produce deterministic evidence.

Tier 2 challenges the green candidate.

When configured, auto-selection prefers a family different from the Task-Spec’s recognized execution_backend; it does not compare against Loop’s actual --agent. An explicit or sole installed judge may be same-family.

Loop settles or refuses.

UPHELD may permit settlement; REFUTED immediately lands BLOCKED. Any later repair or resume is a separate operator action.

POST remains separate.

Plain acceptance returns a verdict without writing Task-Spec or Converge metadata; explicit stamping writes acceptance. Neither form requires the execution receipt, though acceptance still executes declared eval code. The receipt becomes mandatory at the locked done transition.

Independence is reported, not enforced in 0.1.0. Default verifier text prints the judge with its strength; JSON adds independence: independent|same-family|none. Loop consumes the verdict token, not that strength. Policy that truly requires another family must inspect direct verifier output and reject same-family.
UPHELD

The selected judge fails to refute the green candidate under its evidence and rubric. The loop may settle if every other policy holds. UPHELD is still scoped to the checked contract, revision, environment, and reported judge strength.

REFUTED

The judge finds a contract-relevant counterexample, unsupported assertion, or evidence gap. Settlement is refused; the verdict must include enough evidence for a fresh repair attempt or an honest stop.

Unavailable

When no judge engine is installed, low-blast-radius direct verification may return UNAVAILABLE with the absence recorded; high blast radius returns ERROR. Standalone cvg verify exposes --accept-unverified, but Loop has no passthrough for that override. A same-family judge is weaker, not unavailable.

A useful holdout is deliberately under-informed about the worker’s private reasoning and over-informed about the contract, diff, declared evidence, and protected holdout case. This prevents the verifier from merely repeating the implementation story. The verifier’s job is adversarial grading, not code authorship or consensus theater.

How to build an autonomous system

ASD proceeds from authority and observable boundaries, not from selecting a model first.

Define the result and authority.

State what success means, which sources are canonical, the allowed blast radius, and who may approve irreversible actions.

Design the runtime contract.

Separate task identity, capability envelope, budgets, secrets, and settlement rules from worker prose.

Make every action mediated.

Expose narrow tools, validate arguments, enforce paths and permissions, and capture their outputs.

Build the referee before autonomy.

Write executable checks, acceptance gates, trust tiers, and terminal-state mapping.

Add bounded orchestration.

Use fresh workers, checkpointing, retry budgets, stagnation detection, cancellation, and recovery.

Prove failure behavior.

Exercise rejected seals, violated scope, refuted results, stalled loops, unavailable dependencies, and interrupted delivery.

11

Threat model and control boundaries

Agentic safety is mostly ordinary systems engineering applied to a probabilistic planner. The core principle is least authority with independent verification.

Prompt attack

Repository text, tool output, and external content may be hostile instructions. Treat them as data unless the authority chain says otherwise.

Scope escape

Path allowlists, capability envelopes, and HMAC-covered fields define authorization. The portable postflight fence can detect Git-visible repository changes outside declared scope at settlement and refuse success. Ignored or out-of-repository effects require installed runtime, pre-tool, or OS controls; only preventive controls can stop the mutation itself.

False completion

Sealed-eval reruns, settlement path guards, and optional holdouts guard settlement. Terminal output records the outcome; a receipt, when present, records its bounded schema subset and gates later done. Receipt-write failure currently does not suppress SETTLED or LOCAL_SETTLED.

Secret exposure

The harness owns credentials; workers receive only the minimum channel and never print secrets into context or receipts.

Retry runaway

A hard iteration cap, pre-attempt elapsed-work and optional reported-token brakes, cancellation, fresh processes, and stagnation signatures bound retry behavior without claiming in-flight interruption.

Evidence drift

The current receipt binds task/result, Task-Spec and profile hashes, eval-output hash, path-policy verdict, runtime, and time; logs and verifier output supply the rest of the audit trail.

Safe action protocol. Before a material mutation, resolve the exact target read-only, validate it against the runtime contract and repo gate, confirm the operation is reversible or separately authorized, execute the narrowest action, then compare actual effects with expected effects. “The user asked for the feature” is not blanket authority for publishing, deleting, rotating keys, changing trackers, or contacting people.

Defense should be layered around predictable failure modes. The model may misunderstand. Tool output may be malicious. The repository may have changed. A command may partially succeed. The network may disappear after an external write. A verifier may be unavailable. ASD assumes each event can happen and gives the system an idempotency key, recovery pointer, compensating action, or explicit human escalation before it enables unattended operation.

Notice how the worker never receives release credentials and never updates its own Task-Spec to done. The first attempt is valuable even though it fails: its normalized failure evidence gives attempt 2 a precise repair target. The second attempt is not trusted because it looks cleaner: Tier 2 may still refute it and Loop must settle. POST may stamp acceptance independently of the execution receipt; both stamped acceptance and a matching pass receipt must exist before the locked done transition can close the task.

Resume has a documented 0.1.0 boundary. In the resolved workspace, --resume shell-sources state.env when present; otherwise it starts from iteration zero. The current binding is rechecked during eval preflight, but restored state is unauthenticated and not tied to the prior binding, base, workspace, checkpoint, or receipt. Default worktree isolation creates a fresh tree where that state is usually absent, so the run can restart at attempt 1.

Seven misconceptions that break systems

“The model runs tools.”

The harness runs tools after authorizing a model request.

“A stronger model is safer.”

Capability changes the planner. Safety comes from bounded authority and external judgment.

“More context fixes drift.”

Unbounded context adds stale and conflicting state. Fresh attempts plus durable on-disk evidence are cleaner.

“Tests passed, so ship.”

Tests are one part of acceptance; scope, integrity, rollback, and holdout rules may still fail.

“Retry until green.”

Without budgets and stagnation detection, retry is an infinite-cost failure mode.

“The Manager is Pass 7.”

Pass 7 is Bind. A fleet Manager is future orchestration outside the numbered 0–8 chain.

“The CLI is the autonomy.”

The CLI is a control surface and referee. Autonomy emerges from contracts, orchestration, and evidence.

What v0.1.0 proves—and what it does not

The release number unifies the CLI, eleven skills, and Task-Spec distribution. Independent contract identifiers such as format_version: 3 and hmac-sha256-v2 continue to version their own protocols.

Shipped and evidenced
  • Passes 0–8 with Pass 7 Bind and Pass 8 Loop
  • Eleven distributed skills: nine spine + two supporting skills
  • Task-Spec PRE/POST acceptance and HMAC v2
  • Named loop terminal states and bounded attempts
  • Backlog sweep: 9/9 terminal successes, comprising 2 LOCAL_SETTLED and 7 SETTLED
  • Tier 2 paths demonstrated with both UPHELD and REFUTED verdicts
Not current shipped truth
  • The held-out observability-fence verification was REFUTED and remains BLOCKED
  • Fleet Manager as a numbered pass
  • Graph, status, next, CI, work, board, route, or deliver control plane
  • Production-scale autonomous operations proof
  • Removal of the human authority boundary
  • Roadmap designs presented as implemented commands
Evidence boundary. Proving-ground terminal tokens, logs, verifier outputs, commits, and receipts together demonstrate current release behavior in tested conditions. They are not a blanket production reliability claim.

There are two useful readings of the release evidence. The backlog sweep shows the loop can carry a defined set of work to successful terminal states: two local-only settlements and seven ordinary settlements. Separately, the observability-fence holdout shows the system can refuse a claim: the verifier produced REFUTED, so that held-out case remains BLOCKED. Combining those into “everything passed” would erase the most important trust signal in the release.

Evidence to collect next

Longer operations, interruption and resume, more repositories, more provider combinations, contention on shared resources, tracker reconciliation, cost-estimate accuracy, and intentionally adversarial tool output.

Promotion rule

Move a capability from prototype to production only when success and failure paths meet the target operating envelope, recovery has been rehearsed, observability can detect drift, and a human owns rollback and escalation.
