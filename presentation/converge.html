Converge

v0.1.0 · from product intent to verified terminal truth

Converge is a controlled descent from ambiguity to proof. Each pass lowers the altitude, emits a durable artifact, and earns the right to proceed through an executable check. The method preserves human authority while making routine execution safe for agents.

01

The thesis: autonomy needs a method spine

Code generation is not delivery. Delivery requires stable intent, architectural decisions, decomposition, consensus, executable contracts, bounded authority, and independent acceptance.

Before Converge

Intent fragments across chat, tickets, documents, and unstated assumptions. Agents optimize locally and success is narrated after the fact.

Through Converge

Each abstraction becomes a versioned artifact with entry criteria, exit criteria, ownership, and an explicit gate.

After Converge

Implementation terminates in named machine-verifiable states. Attempt logs and checkpoints support recovery; confirmed receipts support review, lifecycle close, reconciliation, and audit.

Convergence is not unanimity. It is the point where intent, architecture, plan, authority, implementation, and evidence agree well enough to proceed under an explicit risk policy.

The method does not eliminate iteration. It changes where iteration happens and what survives it. Early passes iterate on cheap, high-altitude decisions. Later passes iterate on small, sealed units with bounded blast radius. A new worker continues from canonical Task-Specs, attempt logs, checkpoint state, and handoffs; a confirmed receipt is settlement evidence, not the resume checkpoint.

03

System architecture

The method is implemented by four cooperating planes. Each plane has a different source of truth and a different failure mode.

Source hierarchy

Live help establishes the shipped command surface and syntax; executable source and tests establish semantic boundaries. Current skill instructions define role behavior, method docs explain intent, and roadmap documents describe future direction.

Fail-closed hierarchy

The default unattended path blocks on missing authority, failed checks, invalid seals, unresolved objections, or non-accepted results. Explicit supervised or migration waivers remain visible, operator-owned exceptions rather than silent success.

The canonical Pass 0–8 chain

Every pass consumes a particular altitude and emits the next. Pass 0 and Pass 6 are explicit opt-in routes; Pass 4 is always a barrier before executable tasking.

PassVerbPrimary artifactGate / result
0CaptureBRD or no-goCHECK_BRD
1IntentTechnical requirementsCHECK_TECH_SPEC

Entry contract

A pass starts only when the prior artifact is authoritative, current, and complete enough for its altitude. Equivalent approved material may replace a redundant Pass 0 artifact; an informal conversation may not. The operator records why an optional route is skipped.

Exit contract

The artifact exists, has been reviewed in the role appropriate to the pass, and its executable gate returns the documented result. A later edit that changes meaning invalidates downstream assumptions and requires targeted revalidation.

No leapfrogging by artifact volume. A long technical document can still lack product authority; a detailed plan can still lack accepted architecture; a signed task can still be unsafe to run on a host that cannot enforce its binding.
05

Altitude is the organizing principle

A pass should answer only questions appropriate to its altitude. Mixing levels creates artifacts that are hard to review and impossible to gate cleanly.

Problem
BRD

Who needs what outcome, why now, within which scope, measured how?

System
Technical requirements

What observable capabilities, qualities, interfaces, constraints, and failure behavior follow?

Decision
ADRs

Which consequential architecture choices are accepted, with which alternatives and consequences?

Delivery
Swimlane plans

How can coherent work advance independently and integrate safely?

Execution
Task-Spec DAG

What can one executor complete and prove under bounded scope?

Runtime
Contract + receipts

What may a worker do, under which budgets, and what machine evidence settles it?

Common drift: implementation tasks embedded in a BRD, architectural choices hidden inside test prose, or runtime permissions copied into a ticket. Each bypasses the review boundary designed for that question.

A practical review test is to ask, “Could this sentence be approved without knowing the next altitude?” Product outcomes should survive a change of architecture. Technical requirements should survive a change of task decomposition. Task success should survive a change of model provider. Runtime permissions should be replaceable without changing the outcome. When the answer is no, two altitudes have probably been fused.

Trace down

Every low-altitude contract should point upward: a task behavior traces to a plan deliverable, the plan traces to a requirement, the requirement traces to an approved outcome. This makes scope defensible.

Evidence up

Every result should aggregate upward without rewriting history: a terminal token plus a confirmed matching receipt supports task settlement; task evidence supports lane and requirement verification; product evidence informs whether the original outcome was achieved.

06

Shape the work: Passes 0–3

0 · Capture

Decide whether to proceed

Turn an idea into an approved BRD or a principled no-go. Preserve evidence, success measures, constraints, and decision ownership.

1 · Intent

Make technical intent testable

Translate product authority into functional and non-functional requirements without prematurely fragmenting it into tickets.

2 · Structure

Make decisions reviewable

Write ADRs with context, alternatives, consequences, status, and system vocabulary that later plans can rely on.

3 · Decompose

Make delivery parallelizable

Produce dependency-aware swimlane plans with ownership, entry/exit conditions, integration points, risk, and verification.

Honest entry rule. Begin at the earliest pass whose required input is not already represented by an approved equivalent. Skipping a redundant artifact is efficient; skipping unanswered questions is debt.
PassReview lensQuestion that belongs hereQuestion deferred
0Product and decision ownerIs the problem valuable, measurable and inside strategy?Which files will change?
1System behavior and qualitiesWhat must the system do, including failure and operating behavior?Which component implementation wins?
2Architecture and trade-offsWhich consequential decisions are accepted and why?How many executable tasks exist?
3Delivery topologyWhich lanes can advance independently, and where do they synchronize?Which worker or provider runs each task?

Each pass also has a negative output. Capture may produce a no-go. Intent may expose an irreconcilable constraint. Structure may leave an ADR proposed. Decompose may reveal that the initiative cannot be made independently deliverable. Stopping at those points is not process failure; it is the method preventing premature execution.

07

Pass 4: the consensus barrier

The chain deliberately stops before task generation. It is cheaper to challenge a plan than to discover its contradictions across dozens of signed tasks.

Attack assumptions.

Review architecture fit, missing dependencies, ordering, ownership, security, rollback, observability, and acceptance.

Disposition every objection.

Use FIX to change the plan or ACCEPT with a named owner and reason. No REJECT or silent “noted” state passes the gate.

Update the plans.

The hardened artifacts—not the review transcript—become downstream authority.

Record owner sign-off separately.

The owner explicitly accepts residual risk before Pass 5. The machine gate validates the stamped review artifact and plan freshness, not the human act itself.

Consensus means executable agreement. Reviewers do not need identical preferences; they need resolved objections, explicit residual risk, and an accountable owner willing to authorize tasking.
Objection classAdversarial questionAcceptable disposition
CompletenessWhich requirement, failure mode, migration or operating concern has no lane?Add work, narrow scope, or document why the concern is out of scope
TopologyWhere do lanes share mutable state or depend on an unstated integration?Separate responsibility, add dependency, or create an integration lane
VerificationCould every lane claim success while the combined system is wrong?Add cross-lane acceptance and an accountable verifier
SafetyWhat irreversible or externally visible failure can occur?Add authority boundary, rollback, observability and explicit owner
FeasibilityWhich assumption depends on unavailable technology, data, skill or time?Prove it, add a spike, select an alternative, or stop

cvg review --adversary codex,kimi can dispatch different-family reviewers and merge their objections. The machine can widen the attack surface; an accountable owner still decides FIX/ACCEPT dispositions and accepts residual risk. cvg review --check validates cross-family provenance, allowed dispositions, fork compatibility, and current plan hashes, but it cannot verify the separate human owner sign-off. Review dispatch overwrites the canonical objection-log snapshot; preserve earlier reviewed states in Git or an explicit archive.

08

Pass 5: compile plans into Task-Spec

Tasking changes the unit of thought from a plan to an executable contract. Each runnable leaf must be independently delegable, verifiable, and acceptable.

Behavior

Observable requirements with bidirectional links to runnable evals and a final exit check.

Authority

Allowed paths, dependencies, profile, effort, backend, agent, budgets, and HMAC-covered fields. Tier 1 requires a valid keyed digest; structural fallback is weaker.

Lifecycle

ready, in-progress, blocked, done, or parked; an actual transition into done requires stamped acceptance plus a matching passing execution receipt.

Task-Spec is vendor-neutral intent. It deliberately does not embed a specific harness conversation. Pass 7 later derives provider-specific runtime authority while preserving the sealed task identifier.
Find runnable boundaries.

XS, S, M and L are executable leaves; XL and XXL are decomposition nodes. A leaf has one coherent outcome and one independent acceptance boundary.

Build and lint the DAG.

Dependencies represent produced prerequisites, not a preferred meeting order. Run cvg lint for cycles and unsafe overlaps: cvg ready itself filters only status: ready plus completed dependencies, so the dispatcher must require current PRE separately.

Map behavior to evidence.

PRE hard-fails uncovered behaviors and invalid behavior references but only warns when an eval omits verifies:. Run cvg tasks dod to enforce the complete reverse mapping from every eval to authorized behavior.

Bound Task-Spec authority.

Declare touches_paths, creates_paths, profile, effort, backend, agent, budget_iterations, optional budget_tokens, and Validation Card timeout. Loop reads those Task-Spec brakes; Bind hash-binds the source and points to the budget fields without copying their values.

Certify PRE explicitly.

cvg tasks validate checks structure and sizing; plain cvg tasks gate returns a verdict without Task-Spec or Converge metadata writes but still executes eval code. --stamp is mutating: during a re-seal it retires the old signature before validation, then writes a fresh PRE envelope only on pass, so a failed re-seal may require repair and a successful re-stamp.

09

Passes 6–8: project, bind, execute

6 · Register · optional

Project, do not duplicate

Create tracker issues with stable identifiers and backlinks. Task files remain canonical; reconciliation detects drift.

7 · Bind

Constrain runtime authority

Hash-bind the Task-Spec, derive capabilities and provider/settlement policy, emit enforcement artifacts, and produce a compact task-scoped brief. CHECK_RUNTIME_CONTRACT validates this static binding. Before launch, run cvg doctor runtime-contract --runtime <primary> separately: Bind and Loop do not invoke it, and its worktree probe is currently informational to the doctor verdict. Budgets remain canonical in Task-Spec; credentials remain host-owned.

8 · Loop

Run to terminal truth

Use fresh workers, a hard iteration cap, pre-attempt elapsed-work and optional reported-token brakes, stagnation detection, checkpoints, and optional Tier 2 holdout. The current kernel does not interrupt an in-flight process or recheck run counters before Tier 2.

The future Manager remains outside 0–8. Pass 7 is Bind. Fleet-level scheduling, routing, and cross-task orchestration are a future control-plane layer, not a renumbered current pass.
Terminal stateMeaningOperator response
SETTLEDIn a non-dry run, the verified settlement path completed; with external writes allowed, the branch is pushed and either a PR is opened or a manual PR handoff is printed when gh is unavailableInspect the PR handoff and confirm the matching pass receipt exists; then run Task-Spec POST and done before dependents advance
LOCAL_SETTLEDVerified result intentionally remains localConfirm the matching pass receipt, then close Task-Spec separately; publish only with separate authority

Dry-run is a controls preview. Public Loop performs initial setup, prints the resolved run controls, then exits DRY_RUN=OK before worker, eval, settlement, receipt, push, or PR; it emits no TASK_LOOP verdict. Worktree setup/cleanup can occur first, so it is not a strict no-side-effect promise.

Trust is a ladder, not a vibe

Each layer answers a different question. Removing any one of them creates a tempting shortcut from plausible text to uncontrolled mutation.

LayerQuestionMechanismFailure response
IntentIs this the right outcome?BRD approval and owner authorityDo not plan
ArchitectureAre choices explicit and coherent?ADRs and contextResolve decision
ConsensusHas the plan survived adversarial review?Pass 4 objection disposition and stampDo not task
Task integrityHas delegated authority changed?PRE; HMAC v2 at Tier 1, structural-only and supervised at Tier 2Do not execute unattended without Tier 1
Runtime authorityWhich capabilities and policy bind this task?Static Pass 7 envelope + source hash; separate host doctor; credentials remain host-ownedDo not launch
Loop verificationCan sealed proof and independent scrutiny support settlement?Eval, path policy, optional Tier 2, attempted pass-receipt write on settlement pathsRetry, refuse, or confirm missing evidence
Task-Spec acceptanceDoes the settled revision satisfy the original contract?Separate POST verdict and explicit stampReject acceptance; do not transition done
Lifecycle closureDo acceptance and the matching pass receipt both exist?Locked transition … doneRefuse dependency completion
Trust is cumulative and scoped. An accepted ADR does not authorize implementation. A valid HMAC does not prove the task is wise. A passing eval does not prove the worker stayed in scope. An UPHELD holdout may permit Loop settlement but does not stamp Task-Spec acceptance. Each layer supports one claim and relies on the others for the complete assurance case.

The most important operational habit is to preserve negative evidence. A rejected seal, open objection, refuted holdout, blocked dependency, or stalled loop explains why the method stopped. Deleting or softening that evidence to make a dashboard green removes the very signal that distinguishes controlled autonomy from automated optimism.

11

The workspace is the handoff bus

cvg/ lets humans, agents, skills, and commands exchange durable state without depending on private conversation memory.

Versioned truth

BRDs, requirements, ADRs, plans, Task-Specs, runtime contracts, and stamps can be diffed and reviewed.

Rebuildable views

Indexes, queues, and tracker projections derive from canonical files and can be reconstructed.

Accounted evidence

Task lifecycle and Loop event histories are append-only. The current objection log and active task receipt are replaceable snapshots. The receipt writer archives a differing predecessor in its own workspace, but isolated-run sync can overwrite a different destination receipt without archiving it first.

Durable context beats inherited context. A new agent should recover the task from identifiers, canonical artifacts, attempt logs, checkpoint state, handoffs, and any confirmed receipt—not from a hidden chat transcript.

A tracker issue can be excellent for conversation, assignment and visibility while remaining a projection. A model summary can be excellent for orientation while remaining non-authoritative. Converge does not reject those tools; it gives them a clear place so their convenience never silently changes the system of record.

12

The cvg CLI is a referee

The executable surface turns method rules into stable predicates. Human-readable diagnostics explain; exit codes and tokens control automation.

Inside a worker

The CLI helps discover the repository’s method context, inspect tasks, and run permitted checks. These are observations, not self-settlement.

Outside a worker

The orchestrator invokes binding, verification, acceptance, and loop controls independently of the worker’s final narrative.

$ cvg version cvg 0.1.0 (task-spec 0.1.0) $ cvg help # Live help is surface/syntax truth; source + tests define semantic boundaries.
Not shipped today: a broad graph, status, next, ci, work, fleet run/route, rich board, or deliver control plane.
$ cvg agent-context # machine-readable command tree, tokens and exit taxonomy $ cvg tasks validate cvg/tasks/T-20260729-export-format.md $ cvg tasks gate cvg/tasks/T-20260729-export-format.md $ cvg tasks gate --stamp cvg/tasks/T-20260729-export-format.md $ cvg bind --task cvg/tasks/T-20260729-export-format.md $ cvg bind --check --task cvg/tasks/T-20260729-export-format.md $ cvg loop --issue T-20260729-export-format --estimate # configured controls, not a spend forecast; setup first $ cvg loop --issue T-20260729-export-format --resume # source state.env if present; default worktree resume gap may restart attempt 1 $ cvg loop --issue T-20260729-export-format --gate-only --dry-run # controls preview; DRY_RUN=OK before eval/settlement $ cvg loop --issue T-20260729-export-format --agent codex # Pass 8 settles and attempts the pass-receipt write; confirm the file. # Standalone roles: eval=Tier 1, verify=Tier 2; neither settles or transitions: $ cvg eval cvg/tasks/T-20260729-export-format.md $ cvg verify --task cvg/tasks/T-20260729-export-format.md --judge claude # Separate Task-Spec referee and lifecycle steps: $ cvg tasks accept cvg/tasks/T-20260729-export-format.md $ cvg tasks accept --stamp cvg/tasks/T-20260729-export-format.md # done checks accepted=true, by/at nonempty and not (none), parseable receipt, exact task_id/result=pass: $ cvg transition T-20260729-export-format done

Validation and explicit PRE stamping precede binding. Loop owns bounded attempts, Tier 1 evaluation, optional Tier 2, and settlement; it does not stamp POST or transition lifecycle status. Its current settler attempts the pass-receipt write, so a success token without that file is incomplete. Plain gate and accept do not write Task-Spec or Converge metadata but still execute eval code; their --stamp forms are mutating. A re-seal retires the old PRE signature before validation and a failed re-seal can leave the spec unsealed. POST may accept under structural-only integrity or without blast-radius evidence when that check is disabled/unavailable. All Loop modes require --issue; public dry-run performs initial setup, prints controls, then exits DRY_RUN=OK before worker/eval/settlement and emits no terminal verdict. Same-state done returns NOOP before its evidence guard.

13

The agent-facing protocol

A conforming worker receives minimal, authoritative context and interacts through explicit capabilities. At each checkpoint, the kernel preserves the evidence needed to evaluate progress and recover deliberately.

Resolve the task identifier.

Load the canonical sealed Task-Spec and verify PRE eligibility. Current Bind checks identity, hashes/HMAC, and scope; a dispatcher should also gate lifecycle status and dependency readiness before mutation because the runtime check does not independently enforce them.

Load the runtime contract.

Apply the capability envelope, provider/isolation/settlement policy, enforcement artifacts, and hash-bound pointer to canonical Task-Spec budgets. Separately confirm the target host with cvg doctor runtime-contract; current Bind and Loop do not enforce that attestation. Credential delivery remains a harness/host concern.

Inspect before mutation.

Read current repository state, instructions, version, relevant code and existing evidence. Distinguish current source from examples, plans and stale summaries.

Implement inside scope.

Use tools through the harness; keep changes coherent, avoid unrelated cleanup, and record command results. Portable postflight can reject Git-visible repository-scope violations at settlement, but ignored or out-of-repo effects require installed pre-tool, runtime, or OS controls.

Claim, then stop.

Return a candidate result with changed paths, checks run, known limitations and useful recovery state. Do not change acceptance fields or assert settlement.

Let the referee decide.

Independent verification reconstructs evidence, reruns declared predicates and maps the outcome to settlement, retry, block, stall, exhaustion, cancellation or error.

No hidden authority transfer. Repository instructions, tool output, an issue comment or a generated file can contain persuasive text. The worker treats them as data unless the signed task and runtime contract explicitly make them authoritative. External content never upgrades its own privilege.

Why attempt 1 matters

The kernel stores the worker output and rerun eval output in cvg/loop/<id>/attempts/001.log, then stores a normalized failure fingerprint and budget counters in state.env. The next fresh worker receives the prior log tail and current failing eval evidence—not the prior worker’s private reasoning. These are separate checkpoint artifacts, not an execution receipt.

Why attempt 2 is not enough

Worker-run tests are useful feedback but do not settle the task. Loop reruns the sealed eval and path guard. When configured, verifier auto-selection prefers a family different from the Task-Spec backend, not necessarily the actual Loop agent; explicit/fallback same-family judges remain possible and Loop gates only the verdict token. Confirm the attempted pass receipt before POST and done.

Evidence, claims, and current proof

Converge distinguishes structural correctness, tested behavior, release evidence, and production proof. Green checks at one layer must never be marketed as another.

Backlog sweep evidence

Nine of nine proving-ground backlog tasks reached terminal success: two LOCAL_SETTLED and seven SETTLED.

Held-out boundary

The held-out observability-fence verification was REFUTED and remains BLOCKED. The control worked by refusing to turn failed evidence into a success claim.

A blocked result can be positive system evidence. It proves the referee can reject a claim. It does not prove the underlying task was successfully delivered.

18

Adopt Converge without ceremony

Start with the evidence boundary that removes the most risk, then expand upstream and downstream. The method is valuable when each artifact changes a decision—not when it only adds pages.

Baseline live truth.

Run version/help, inspect the current repository, identify existing authority, and mark roadmap-only concepts. Treat help as surface/syntax evidence and source/tests as semantic evidence.

Select the entry pass.

Reuse approved inputs and begin where material unanswered questions start.

Install one hard barrier.

Make consensus and task PRE non-bypassable before unattended work.

Make acceptance executable.

Build behavior/eval traceability, POST checks, blast-radius inspection, and named results.

Bind runtime authority.

Keep budgets and routing canonical in Task-Spec; derive capability, provider, and settlement policy in Bind; keep credentials host/harness-owned.

Add bounded loops last.

Only after deterministic gates exist should retries, holdouts, checkpoints, and wider autonomy be enabled.

The maturity test: a new human or agent can identify the current task, its authority, its allowed actions, its evidence, and its next valid transition without reading a private conversation.
