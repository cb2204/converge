Autonomous System Development

the Agentic Loop · the five layers · how the machine gets built  ·  v1.0  ·  2026-07-17  ·  every demo output on this page is a real run receipt

The model thinks, the harness acts, the referee judges — and the only things that ever cross between them are text and exit codes. This deck teaches the runtime anatomy (the Agentic Loop) and the build discipline (ASD) behind cvg — with runnable, zero-API-key demos you can break yourself.

01Three names, three questions — never blur them

Most confusion in agentic engineering comes from mashing these three together. Each answers a different question.

LevelQuestion it answersNameNature
1 · RuntimeHow does a running agentic system work?The Agentic Loop (five layers)anatomy — nothing is "developed" while it runs
2 · Product methodHow does the system deliver any project?Converge (8 passes, brief → fleet green)workflow the finished system executes
3 · Meta-processHow do you build the autonomous system itself?ASD — Autonomous System Developmentthe discipline this deck codifies (Phases 0–3)
Why "System", not "Agent". An agent is one loop instance (layers 1–4). What gets built is the system: orchestrator + harness + referee + method — and the referee/orchestrator parts are precisely what makes it autonomous.
02The five layers — who thinks, who acts, who judges

Layers 1–4 are industry-standard. Layer 5 is the one most teams skip — and it is the entire trust story.

L1MODELOpus / Fable / GPT — a pure text function: tokens in → tokens out. Stateless. No hands, no shell, no memory between calls.
L2HARNESSClaude Code / Codex CLI — a NORMAL PROGRAM. Owns the API key, the while-loop, the conversation state, permissions, sandboxing.
L3TOOLSBash, file edit, MCP servers — functions the harness offers the model as text descriptions (schemas) in every prompt.
L4ENVIRONMENTFilesystem, git, databases, YOUR cvg CLI — what the tools act on.
L5REFEREEGates, evals, HMAC seals, CI re-runs — deterministic code that judges outcomes. Exit 0/1 decides; the model's opinion is never consulted.
03The Agentic Loop — the corrected hop map

The while-loop is not a hop — it wraps hops 1–4. And the single most common misconception in the field: the model never invokes anything. It asks (Hop 2); the harness calls (Hop 3).

Hop 0 CHAT (or a scheduler — anything that starts a turn) Hop 1 HARNESS ASSEMBLES one big text prompt: ┐ system + tool schemas + AGENTS.md/skills + │ ENTIRE conversation + your message │ Hop 2 MODEL EMITS — plain text OR a request blob: │ ← THE WHILE-LOOP {"name":"bash","input":{"command":"cvg ..."}} │ wraps hops 1–4, Hop 3 HARNESS EXECUTES — permission check, subprocess, │ repeating until capture stdout/stderr/exit code │ Hop 2 returns Hop 4 RESULT → TRANSCRIPT, go to Hop 1 ┘ plain text Hop 5 REFEREE JUDGES the outcome — exit 0/1, independent of the loop
Agent = model + while-loop + tools. Nothing more mystical. The separation at Hop 2/3 is where ALL safety lives: sandboxing, permission prompts, and logging are harness features, possible only because the model cannot act directly.
04Receipt — a complete agentic system in 40 lines

docs/demos/agentic-loop.py — the model is FAKE (scripted) so the loop machinery is visible with zero API keys. Swap fake_model() for an HTTPS call and this IS Claude Code, minus polish. Real output from this repo:

$ python3 docs/demos/agentic-loop.pyUSER : What is the paid revenue in the fixture? MODEL EMITS : {"command": "sqlite3 tests/e2e-test-engine/data/toy.db \"SELECT printf('%.2f', sum(paid_amount)) FROM silver_orders WHERE is_paid=1;\""} HARNESS RAN IT: exit 0 | output: 240.00 AGENT (final) : The paid revenue in the fixture is 240.00.
Read that middle line again. The model produced a JSON blob — that is ALL a model can ever do. A plain subprocess call ran the command. The homework: edit the fake model to emit a wrong command and watch the harness dutifully run it — you will feel why Layer 5 is non-negotiable.
05How the model "knows" to invoke the CLI

Nobody wires the model to cvg. Three mechanisms — all just text placed in the context window. Remove the words, the knowledge vanishes.

① Tool schemas
  • injected into EVERY request
  • "Bash takes {command}, returns output"
  • the model was RL-trained to emit well-formed calls when a task needs one
② Ambient docs
  • AGENTS.md, CLAUDE.md, skill descriptions
  • "this repo has cvg; Pass 1 = cvg intent"
  • why AGENTS.md is in 60k+ repos — the context window is the model's only interface to your world
③ Runtime discovery
  • the model explores like a human: emit ls bin/, read output, emit cvg help
  • discovery through the same loop
06The two seats of cvg — inside and outside the loop

The same binary occupies two completely different positions relative to the loop. This is the part nobody teaches.

Seat A · INSIDE — cvg as a tool

During hops 2–3 the model emits {"command":"cvg tasks gate T-1.md"} and the harness runs it — cvg is just another program in the environment, like sqlite3 in the demo. This is Track R's mode today.

Seat B · OUTSIDE — cvg as launcher + referee

cvg work T-1 --engine claude: pre-gate the seal → frame the prompt → spawn an entire agentic loop as one subprocess → ignore its self-report → run the referee itself → done / retry / park. This is the autonomous mode.

the complete nesting, top to bottom: cron / you ← the trigger └─ cvg run ← ORCHESTRATOR: picks ready tasks └─ cvg work T-1 --engine claude ← LAUNCHER + REFEREE (Seat B) ├─ pre-gate: HMAC seal check ├─ spawn ▶ THE AGENTIC LOOP (hops 1–4 repeating) │ └─ inside, the model may call cvg eval (Seat A, nested) ├─ post-gate: referee re-runs evals — exit 0/1 decides └─ done / retry (budget-bounded) / park
07Receipt — the launcher never believes the thinker

docs/demos/launcher.sh — Seat B in miniature. Real output: the loop self-reports, the launcher ignores it and re-verifies against the world.

$ bash docs/demos/launcher.sh[cvg-work mini] step 1: spawning the whole agentic loop as a subprocess... [cvg-work mini] loop finished. Its SELF-REPORT was: AGENT (final) : The paid revenue in the fixture is 240.00. [cvg-work mini] step 2: REFEREE runs independently (ignore the self-report): SMOKE: PASS (tables 3/6/4, silver ok, paid revenue = 240.00) [cvg-work mini] verdict: VERIFIED -> task would move to done
cvg work in one sentence: spawn the thinker, never believe it, check the world. If verification only happened inside the loop, the transcript could claim anything — independence of the referee is the whole trust model.

09ASD — the end-to-end build discipline

Counterintuitive on purpose, and the opposite of what most teams do: validate the method before wrapping it, harden the machine on a fixture before real work, remove the human last — one gate at a time.

Phase 0
Foundations
before any AI touches anything
  • 0.1 name the anatomy — own the referee + method, rent the models
  • 0.2 write the contract file (one file = the law; rules of engagement)
  • 0.3 build the test floor — deterministic fixture, control sums, DESIGNED failures
  • 0.4 stage a real proving ground — floor tests the machine; proving ground tests the method
Phase 1
Method validation
Track R · five beats per pass
  • ① UNDERSTAND — audit the skill vs the field, hardening list
  • ② RUN — for real, on the proving ground, human judging
  • ③ CANONIZE — skill = blueprint; gate goes green
  • ④ IMPLEMENT — thin CLI subcommand (frame→dispatch→collect→gate)
  • ⑤ PROVE — CLI re-run must DIFF-MATCH the manual golden run
Phase 2
Machine hardening
Track M · fixture only
  • 2.1 trust — CI re-runs every eval in a clean container
  • 2.2 one worker — engine adapters, L2 conformant (parks, never spins)
  • 2.3 the Manager — stateless tick, locks, worktrees, overlap serialization
  • 2.4 visibility — board + event ledger
  • 2.5 depth — tier-2 cross-engine judge, injection defense
Phase 3
Autonomy graduation
remove yourself one gate at a time
  • 3.1 scheduler replaces the human trigger (cron / CI)
  • 3.2 humans remain only where severity demands (tier-3 by blast radius)
  • 3.3 receipts feed routing — measured cost/quality picks the engine
  • 3.4 sustain loop — re-run all evals on schedule; drift reopens work
10The invariants — the actual doctrine

The phases are just the order of construction; these six hold through every phase.

1eval defines donenever the model's claim, never your feeling — exit 0 from a sealed check
2evals discriminateanything that passes before the work exists is a broken check, not a pass
3state lives outsidefiles, git, tracker — "memory" is re-injected text; the model is stateless
4one writer per statethe CLI writes, the board renders, the model asks — never blurred
5automate triggers, not judgmentjudgment gets gates (H1/H2/tier-3); only the trigger gets a scheduler
6own every layera harness you can't explain is a harness you can't trust — understanding is a deliverable
